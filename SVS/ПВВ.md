# ПВВ — процессор ввода-вывода СВС: форматы заявок, режимы работы, взаимодействие с АДАП

Документ описывает протокол между центральным процессором СВС (программа **АДАП**)
и канальным процессором **ПВВ** в том виде, в каком он восстановлен по исходному
тексту АДАП-а и по прогонам эмулятора. На этот документ ссылаются комментарии в
`svs_iom.c` (`§5.2`, `§5.4`, `§5.6`) и `svs_disk.c` (`§5`).

## 1. Статус сведений

Протокол ПВВ не опубликован; всё изложенное ниже — реконструкция. Каждое
утверждение снабжено пометкой о том, чем оно подтверждено:

| Пометка | Что означает |
|---|---|
| **[К]** | Код эмулятора: реализация команды в `svs_cpu.c` / `svs_mmu.c`. Достоверно по построению. |
| **[Н]** | Наблюдение в прогоне `dispak.ini` (трасса `dispak.trace`, дампы памяти). Достоверно для текущей конфигурации. |
| **[Л]** | Листинг компиляции `adapcmp.b6` (совпадает побайтно с настоящим `adap.b6`). Достоверно как намерение АДАП-а. |
| **[?]** | Вывод/догадка, прямо не проверенная. |

Источники: `adapcmp.b6` (реконструированный исходник АДАП-а),
`besm6.github.io/sources/dispak-svs/adap.txt` (компилированный листинг настоящего
АДАП-а — та же логика по другим адресам), `svs_iom.c`, `svs_disk.c`.

## 2. Действующие лица

- **СВС** — центральный процессор. Исполняет **АДАП** — резидентную программу
  диспетчера ввода-вывода, занимающую страницы 12–15 (физ. 030000–037777).
- **ПВВ** — процессор ввода-вывода (канал). В реальной машине — отдельный
  процессор со своей памятью; в эмуляторе — `svs_iom.c`, работающий прямо по
  физической памяти СВС.
- Связь двусторонняя и асинхронная: СВС → ПВВ через **командное слово БАК**
  плюс «звонок в дверь» (`РЕГ '50'`); ПВВ → СВС через **внешнее прерывание**
  (ГРВП разр.3) плюс структуры в памяти.

## 3. Представление данных

### 3.1. Ячейка памяти: значение и тег **[К]**

Каждое 48-разрядное слово хранится в 64-разрядной ячейке `memory[]` как

```
memory[a] = (значение48 << 16) | тег16
```

Аппаратный тег (`TAG_INSN48`=035, `TAG_NUMBER48`=036) лежит отдельно, в массиве
`tag[]`. Поле `тег16` внутри слова — **не** аппаратный тег, а 16 разрядов
данных, доступных программе через РМР.

Это разделение — основа всего протокола: указатели и номера устройств АДАП
передаёт именно в `тег16`, а данные обмена — в `значение48`.

### 3.2. Команды, работающие с парой «значение/тег» **[К]**

| Команда | Код | Действие |
|---|---|---|
| `СЧП` | 033 | `ACC = значение48`, `РМР = тег16 << 32` |
| `СОП` | 046 (ф.2) | то же |
| `СЧМР` | 031 | `ACC = РМР` — прочитать сохранённый `тег16` |
| `ЗПП` | 032 | записать `(ACC<<16) \| ((РМР>>32) & 0xFFFF)` |

Типичная связка «достать тег»: `СЧП x; СЧМР; СДА 64+n; И =маска`.
После `СЧП` тег стоит в разр.33–48, поэтому сдвиг вправо на `32+k` даёт
`тег16 >> k`.

### 3.3. Сдвиг `СДА` **[К]**

`n = (Aex & 0177) - 64`; **положительное `n` — сдвиг вправо**, отрицательное —
влево. То есть `СДА 64+38` — вправо на 38, `СДА 64-1` — влево на 1.

### 3.4. Аппаратный стек: регистр 017 **[К]**

Регистр `М17` (017₈ = 15) — указатель стека; операнд вида `(S)`/`(17)`
автоинкрементируется при записи и автодекрементируется при чтении.

| Команда | Код | Действие |
|---|---|---|
| `СЧИМ` | 043 | **PUSH ACC**, затем `ACC := M[операнд]` |
| `ЗП (S)` | 000 | PUSH ACC |
| `НТЖ (S)` | 012 | **POP**, `ACC ^= снятое` |
| `УИМ` | 041 | POP в регистр |

Важно: `СЧИМ X` — это «протолкнуть текущий ACC и загрузить X», а не просто
загрузка. Пара `СЧИМ X; НТЖ (S)` вычисляет `X ^ (то, что было в ACC)`.
Именно она реализует вторую проверку в `ВЫППВВ` (§7.3).

### 3.5. Приписка страниц **[К]**

`УИА`/`vtm` с регистром 0 в режиме супервизора попутно пишет разряды ССП из
`addr & (PSW_INTR_DISABLE|PSW_MMAP_DISABLE|PSW_PROT_DISABLE)`. Отсюда идиома
АДАП-а: `VТМ 1024` — приписка **включена**, `VТМ 1027` — **выключена**.
Разряды ССП (восьмерично): `MMAP_DISABLE`=1, `PROT_DISABLE`=2,
`CHECK_HALT`=10, `INTR_DISABLE`=2000.

### 3.6. Макрос `ДАЙМА` **[Л]**

```
ДАЙМА:  СЧМР ; ПО skip ; СДА 64+32 ; ДМА ПМА
```

Извлекает указатель, закодированный в `тег16`: адрес хранится как
`z + A(ПМА)`, а `ДАЙМА` возвращает `тег16 - A(ПМА) = z`. `ПМА` = 032102.
В `svs_iom.c` тому же служит `IOM_DAIMA(v) = v & 077777`.

## 4. Инициализация: командное слово БАК и регистрация таблиц

### 4.1. Как СВС отдаёт команду каналу **[Л][Н]**

АДАП строит командное слово (adap.bemsh:2960-2965) как
«адрес блока `БАКПВВ` с точки зрения ПВВ **ИЛИ** КОП», затем `СДА 64+16; ЗПП`.
Из-за сдвига вправо на 16 **значащие 48 разрядов оказываются в младшей
половине** 64-разрядной ячейки — противоположно словам данных (§3.1).

Слово кладётся в `СТБАК` (0100₈, поле `iom->HA`), после чего следует звонок:
`СЧ ЕПВВ; РЕГ '50'`.

Формат командного слова:

```
разр. 1..36   адрес 2-словного блока БАКПВВ (физический; макрос ДФАПВВ
              прибавил базу АДРЕС = 030100). Здесь же флаги СЕМБИТ (разр.17)
              и ПОБ (разр.21).
разр. 37..44  КОП — код операции (база М36, младший разряд = разр.37)
```

### 4.2. Коды КОП **[Н]**

| КОП | Смысл | Куда попадает |
|---|---|---|
| 004 | инициализация БАК (указатель на БАКПВВ) | обрабатывается через `СТБАК` |
| 005 | регистрация **таблицы устройств** | `iom->UTA`; наблюдалось `УТ@030360` = **ТУС** |
| 006 | регистрация **таблицы очередей** | `iom->IOQA`; наблюдалось `ТОЧ@030540` = **ТОЧ** |
| 007 | регистрация **таблицы ответов** | `iom->SQA`; наблюдалось `ОТВ@031350` = **ДВРПВВ** |
| 015 | управляющая команда без адреса | запускает обслуживание ЕСВС/ТВЗП |
| 016 | `ПУСКОБ` — пуск обмена по очереди ТОЧ | `iom_pusk_obmen()` |

> Адреса этих трёх таблиц **не должны быть зашиты в эмуляторе** — канал узнаёт
> их от самого АДАП-а командами 005/006/007. Исключение — `ТВЗП` (031270):
> для неё команды регистрации не наблюдалось, поэтому адрес пока константа
> `IOM_TVZP` (см. §9.3).

## 5. Обмен

### 5.1. Общая схема

```
       АДАП (СВС)                                   ПВВ (канал)
  ФОРБВВ: собрать заявку  ──┐
  ВКЛТОЧ: выбрать путь      │
     НУС=0 → ОТДАЮЗ ────────┼──► ТВЗП[НСВС] + СЕМБИТ, звонок РЕГ '50'
     НУС≠0 → НУСЕС ─────────┴──► ТОЧ[2·НУС] (НОЧ/КОЧ), затем ПУСКОБ
                                        │
                                        ▼
                                  выполнить обмен с устройством
                                  записать ДР/ДРУ (сл.5/6)
                                  взвести АКТЗ (сл.7)
                                  связать заявку в ДВРПВВ
                                  ГРВП разр.3 (GRVP_INTR_IOM)
                                        │
  Я501 ◄────────────────────────────────┘
  ОБРПРЕ → ПРПВВ → ППВВ → ГАСИПР → АКТИВ → ВЫППВВ → ИНДБУД → РАСПАК
```

### 5.2. Блок заявки (БВВ) и очереди ТОЧ

Заявка — **8-словный блок, выровненный на 8** **[Л][Н]**. В текущей
конфигурации единственная заявка лежит по `А(ЗАЯВКИ)` = **031100**
(из `АЗАЯВК`@031601).

| Слово | Имя | Содержимое |
|---|---|---|
| 0 | — | связь со следующей заявкой (извлекается `ДАЙМА`, §3.6) |
| 1 | — | *(не наблюдалось)* |
| 2 | **ДО** | дескриптор данных: адрес буфера ОП (разр.1–15) и длина |
| 3 | **СО** | управление обменом; разр.48 = чтение (ТЕГ48) |
| 4 | **СПУ** | физический адрес зоны; см. §5.4 |
| 5 | **ДР** | ответ устройства (заполняет канал); в `тег16` — НУС, см. §5.5 |
| 6 | **ДРУ** | ответ устройства, продолжение |
| 7 | — | признаки; **АКТЗ** = М20В'1' = 04000000; направление+устройство в разр.42–47 (`СБР =М39В'7'М7В'7'`); номер драйвера; НЗАД |

**ТОЧ** — таблица очередей, **по 2 слова на устройство**: `НОЧ` (начало) и
`КОЧ` (конец) списка заявок. Индекс — **2·НУС** **[Л]** (КАНСОВ,
adap.bemsh:2153). Заявки связаны в список через слово 0.

В указателях старшие разряды несут признаки, в частности **СЕМБИТ**
(разр.17 = 0200000) — семафор занятости; значащий адрес выделяется
маской `& 077777`.

### 5.3. Таблицы устройств ТУСЗ / ТУС и номер НУС **[Н]**

Это центральная структура, и до сих пор она была описана неверно. Реальное
устройство (дамп в точке `ИНДБУД`, см. §10):

```
ТУСЗ = 030200, 112 слов (0160₈): 030200 … 030357
ТУС  = 030360, 112 слов (0160₈): 030360 … 030537
```

Таблицы **параллельны**: запись `ТУСЗ[i]` и `ТУС[i]` описывают одно устройство,
расстояние между ними ровно 0160₈. Каждая разбита на **7 блоков по 16 записей**
— по блоку на класс устройства:

| Смещение | Адрес в ТУС | Адрес в ТУСЗ | Класс | КАНАЛ (разр.33–38 ТУСЗ) |
|---|---|---|---|---|
| 000 | 030360 | 030200 | — | (частично заполнен) |
| 020 | 030400 | 030220 | 1 | 0x01 |
| 040 | 030420 | 030240 | 2 | 0x0C |
| 060 | 030440 | 030260 | 3 | 0x0D |
| 100 | 030460 | 030300 | 4 | 0x20 |
| **120** | **030500** | **030320** | **5 — МД (диск)** | **0x22** |
| 140 | 030520 | 030340 | 6 | 0x24 |

Блок МД по смещению 0120 — это и есть символ **ТУСМД** (030500) из исходника;
его начальное значение в `adap.b6` содержит `М32Х'22'`, то есть номер канала
0x22 задан на этапе компиляции **[Л]**.

**Формат записи ТУС** (после обработки, §5.3.1): старшее поле — **кольцевая
ссылка** на следующую запись блока:

```
ссылка = (смещение_следующей_записи_от_ТУС) * 4 + 2
```

Например `ТУС[0120]`=030500 содержит `0506…`: следующая запись имеет смещение
0121, `0121*4+2 = 0506`. Последняя запись блока (030517) ссылается обратно на
первую (`0502`) — кольцо из 16 записей.

**Номер устройства НУС** — это **индекс записи в ТУС/ТУСЗ**, а не номер
устройства на шине:

```
НУС = смещение_блока_класса + номер_устройства_внутри_класса
```

Для системного диска (класс МД) базовое смещение — **0120₈**. Это подтверждено
дважды **[Н]**: обе проверки в `ВЫППВВ` проходят (§7.3), и `ИНДБУД` находит
канал 0x22 в `БУДКАН` ровно за 18 итераций — по индексу 17, где `0x22` и стоит
(§7.4).

> Младшие 4 разряда НУС — номер устройства внутри класса; `ВЫППВВ` сверяет их
> с разрядами 39–42 слова СПУ, которое строит сам АДАП (§7.3). Поэтому канал
> обязан брать это поле **из заявки**, а не из внешнего параметра.

#### 5.3.1. Как АДАП получает НУС: ЛНУТУС → ЛОКОБ → ТОУ **[Н][Л]**

НУС не задаётся снаружи — АДАП вычисляет его из **логического номера
устройства (ЛУ)**:

```
ФОРБВВ: СЧИ НУС ; ПВ ЛНУТУС     (34615)   ЛУ на входе в сумматоре
ЛНУТУС (34413) → ЛОКОБ (34107) → таблица ТОУ (31465)
```

**ТОУ** — ТАБЛИЦА ОБЩИХ УСТРОЙСТВ, индексируется типом устройства (`ТИП`;
`МДТИП ЭКВ 0`, поэтому МД — нулевая запись, 031465). Формат записи:

```
ТОУ[МД] = 0003006000400120   М35В'06' М25В'30' М15В'04' В'120'      МД 30-33
            разр.26-31 = 030   первый логический номер
            разр.16-18 = 4     сколько устройств
            разр.1-7   = 0120  база блока в ТУС
```

То есть МД занимает **логические номера 030-033**, отображаемые на индексы
ТУС **0120-0123**. `ЛОКОБ` линейно обходит диапазоны ТОУ и возвращает
`НУС = база + (ЛУ − первый)`. Если ЛУ ни в один диапазон не попал, НУС=0, и
`ВКЛТОЧ` уходит ветвью `ОТДАЮЗ` (§6).

Соответствующие записи МД в **ТЛУ** (таблица ЛОКАЛЬНЫХ устройств) нулевые —
диск является общим, а не локальным устройством.

**Кодировка ЛУ в НАПРУС.** ФОРБВВ собирает логический номер командой
`СБР =М39В'7'М7В'7'` (34607), то есть из разрядов **42,41,40 и 10,9,8**
(старший→младший). Поэтому:

| ЛУ | НАПРУС |
|---|---|
| 030 | `0030000000000000` |
| **031** | **`0030000000000200`** |
| 032 | `0030000000000400` |
| 033 | `0030000000000600` |

Прежнее значение `d 30115 1` не затрагивало ни одного из этих разрядов, ЛУ
получался нулевым, и заявка всегда уходила в `ОТДАЮЗ`.

#### 5.3.2. Маска СВС-владельца и номер машины **[Н][Л]**

Пройдя `ВКЛТОЧ`→`НУСЕС`, заявка попадает в `ДИСПАК` (034301), где проверяется,
принадлежит ли устройство этой машине:

```
34301  МОДА ТУСЗ ; СЧП (НУС)
34302  ПО ОТДАЮЗ        ТУС НЕ ОПРЕДЕЛЕН        ← ТУСЗ[НУС] == 0
       СДА 64-26        разр.7-16 → позиция 33-42 (МАСКА СВС)
...
34305  СЧ ЕСВС ; СДА 64(НСВС) ; И (S)
34306  ПЕ ОТДАЮЗ        НЕДОСТУПНО ДЛЯ ОС       ← бит своего СВС стоит в маске
       ПБ ТЕСОБМ
```

`ЕСВС` (031567) = `0040000000000000` — единица в разр.42, сдвигаемая вправо на
`НСВС`. Маска владельца для МД (разр.7-16 записи ТУСЗ) равна **01177**:

| НСВС | разряд | бит маски | итог |
|---|---|---|---|
| 0 | 42 | 1 | `ОТДАЮЗ` — диском не владеет |
| **1** | 41 | **0** | **`ТЕСОБМ`** — владеет |
| 2 | 40 | 0 | `ТЕСОБМ` — владеет |
| 3 | 39 | 1 | `ОТДАЮЗ` |

Номер машины АДАП читает командой `РЕГ '250'` (позиционный код: номер
кодируется НУЛЁМ в своей позиции среди единиц). В эмуляторе он берётся из
**`cpu_svs_number`** — регистр `NSVS`, задаётся из .ini как `d NSVS 1`.
Эмулятор исполняет одну машину за раз, но её номер выбирается.

#### 5.3.3. Учёт активных заявок: ЧАКБВВ **[Л][Н]**

На локальном пути АДАП сам увеличивает счётчик активных заявок канала
(разр.1-10 записи `БУДКАН`) перед выдачей команды:

```
34316  ИЛИ (Ц)
       СЛЦ =В'1'     УВЕЛИЧИЛ СЧ-К АКТИВНЫХ БВВ
34317  ЗП (Ц)
       СЧПР БАКПВВ
```

`Ц` указывает на запись БУДКАН, найденную вызовом `ИНДБУД` двумя командами
ранее. При завершении `ВЫППВВ` уменьшает этот счётчик (032526) и требует,
чтобы он был ненулевым, иначе `ОШД12`. Поэтому канал **не должен** вести этот
счётчик сам: на своём пути АДАП делает это без посторонней помощи.

#### 5.3.4. РОСТУС — формирование ссылок **[Н][Л]**

Подпрограмма `РОСТУС` (036050, «ФОРМИР ССЫЛОК») **преобразует уже загруженную
ТУС на месте**: читает `ТУС[i]`, выделяет поле «СМЕСЬ» (`И =В'7'`), и
записывает обратно ссылку на следующую запись. Она **не** заполняет ТУС из
ТУСМД — ТУСМД есть часть ТУС. В прогоне выполняется 112 раз (по одной
итерации на запись), что ровно соответствует размеру таблицы.

Ранее считалось, что `РОСТУС` не достигается, а `ТУС`/`ТУСЗ` пусты. И то и
другое неверно: проверка велась по адресам 030200/030360 — это **пустые головы**
таблиц (блок класса 0), тогда как содержимое начинается со смещения 020.

### 5.4. Описатель обмена: ДО, СО, СПУ

Наблюдённая заявка **[Н]** (`iom0 --- обмен: устр=1 заявка@31100 ЧТ зона=511 буфер=42016`):

```
ДО  = 0000000000142016   (РМР 002360)
СО  = 5014000000000000
СПУ = 0001212000200000   (РМР 001222)
```

- **ДО** — разр.1–15 дают адрес буфера ОП (`042016`); старшая часть — длина.
- **СО** — направление и режим. В единственной наблюдённой заявке (чтение)
  установлены **разр.39, 40, 46, 48** — что совпадает с признаком «ТЕГ48 чтение
  = разр.39,40,46,48» из комментария `svs_iom.c`. Канал сейчас различает
  направление **только по разр.48** (`is_read = (so >> 47) & 1`); остальные три
  разряда не проверяются. Признак записи (по тому же комментарию — разр.39,40)
  **не наблюдался ни разу** **[?]**, поэтому на чём именно чтение и запись
  различимы — по одному разр.48 или по всей четвёрке — этими данными не
  устанавливается.
- **СПУ** — физический адрес зоны. Сам номер зоны канал берёт **не из
  значения48, а из `тег16`** (`memory[z+4] & 0xFFFF` = 001222) — это и есть
  «копия младших 16 разр. адреса в РМР». Зона удвоена, поэтому
  `зона = тег16 >> 1` = 0611 → 511₈.
  Множитель зависит от **типа ёмкости устройства**, который положено брать из
  `ТУСЗ[НУС]`; сейчас он не читается, а делитель 2 зашит **[?]** — см. §9.2.
- Разряды 39–42 значения48 СПУ — номер устройства внутри класса, сверяемый
  в `ВЫППВВ` (§7.3). В наблюдённой заявке это поле **равно 0**.

Зона на диске — 8 служебных слов + 1024 слова данных; канал вызывает
`svs_disk_io(dev, zone, memaddr, memaddr+8, …)`.

### 5.5. Ответ канала: ДР, ДРУ, АКТЗ, ДВРПВВ

Завершив обмен, канал обязан сделать **четыре** вещи **[Н]** — пропуск любой
из них уводит АДАП в обработчик ошибки:

1. **ДР (сл.5)** — `значение48` = код завершения (0 — успех), `тег16` = `НУС << 2`.
   `ВЫППВВ` читает `НУС = (тег16 >> 2) & 01777`.
2. **ДРУ (сл.6)** — продолжение ответа. Назначение разрядов не установлено **[?]**;
   сейчас пишется 0, и `ВЫППВВ` это принимает.
3. **АКТЗ (сл.7)** — взвести признак «активная заявка» (М20В'1' = 04000000)
   в `значение48`. Без него `ГАСИПР` считает, что встретил заявку впервые,
   сам взводит АКТЗ и уходит на `ОШДВРО` (сброс канала).
4. **Связать заявку с ДВРПВВ** — головой очереди завершённых заявок,
   зарегистрированной командой КОП=007 (`iom->SQA`, наблюдалось 031350):

   ```
   значение48 = (z - ПВВ) << 17     где ПВВ = 030000
   тег16      = z + A(ПМА)          где A(ПМА) = 032102
   ```

   Смещение относительно `ПВВ` обязательно: `ГАСИПР` после выделения поля АН
   делает `ДМА` (= `ВЧ АДРЕС`), а `память[АДРЕС]` хранит `−ПВВ`, так что из
   `(z−ПВВ)` получается абсолютный `z`. Если положить туда голый `z`,
   на выходе будет `z+ПВВ`.

Затем канал поднимает внешнее прерывание: `ГРВП |= GRVP_INTR_IOM` (разр.3).

### 5.6. Сводка форматов командного слова

См. §4.1 (разряды) и §4.2 (таблица КОП). Ключевое отличие от слов данных:
у командного слова БАК значащие 48 разрядов лежат в **младшей** половине
64-разрядной ячейки, у слов данных — в **старшей**.

## 6. Два режима подачи заявки **[Л]**

`ВКЛТОЧ` (adap.bemsh) ветвится по НУС:

- **НУС = 0 → `ОТДАЮЗ`.** Заявка кладётся в `ТВЗП[НСВС]` с признаком `СЕМБИТ`
  (разр.17), после чего звонок `ДАЙ ЕСВС; РЕГ '50'`. Это путь «отдать заявку
  другой СВС» — короткий, в обход очередей ТОЧ.
- **НУС ≠ 0 → `НУСЕС`.** Заявка ставится в очередь `ТОЧ[2·НУС]` (НОЧ/КОЧ), и
  обмен запускается командой `ПУСКОБ` (КОП=016).

В текущей конфигурации `dispak.ini` системный диск приходит в `ВКЛТОЧ`
с **НУС = 0** и уходит по ветви `ОТДАЮЗ`; поэтому ТОЧ пуста, а `ПУСКОБ`
вхолостую. Это и есть корень оставшейся проблемы — см. §8.

## 7. Обработка завершения на стороне АДАП

### 7.1. Приём прерывания **[Л][К]**

АДАП сам ставит свои векторы (adapcmp.b6:1404-1407):
`СЧ ВНЕПР; ЗП Я501` и `СЧ ВНУПР; ЗП Я500`. Вектор 0500 — внутреннее
прерывание (РПР), 0501 — внешнее (ГРВП). `ВНЕПР` = `ЗП СМ1; ПБ ОБРПРЕ`.

Разряды ГРВП: `PANEL_REQ`=0001, **`INTR_IOM`=0004**, `TIMER`=0010,
`REQUEST`=0200; наблюдавшаяся маска ГРМ = 0277.

Прерывание доставляется только при (`svs_cpu.c`):

```c
if (!iintr && !(RUU & RUU_RIGHT_INSTR) && !(M[PSW] & PSW_INTR_DISABLE)) …
```

то есть **при выключенном разряде `PSW_INTR_DISABLE` (2000₈)** и не на правой
команде слова. Если АДАП крутится с запретом прерываний, поднятый `INTR_IOM`
просто ждёт.

### 7.2. Диспетчеризация **[Л][Н]**

`ОБРПРЕ` (032275) читает ГРВП (`РЕГ '247'`) и ГРМ (`РЕГ '246'`), нормализует
(`НЕД`) и вычисляемым переходом уходит в таблицу из 6 входов `ПРКЛПР`:
`ПРСВС / СТ102 / АВСВС / СТ102 / ПРВРЕМ / ПРПВВ`. Разряду 3 соответствует
`ПРПВВ` → `ППВВ` (032334).

`ППВВ` начинается с `СЧСНХ ДВРПВВ; ЗППР ДВРОС` — то есть **ДВРОС (031347) есть
копия ДВРПВВ (031350)**. Канал обязан писать в ДВРПВВ; в ДВРОС писать
бесполезно, его перезапишут.

Далее: `ГАСИПР`(032400) → `АКТИВ`(032410) → `ППВВИН`(032423) →
`БЕЗОШБ`(032470) → `ВЫППВВ`(032514) → `ИНДБУД`(035427) → `РАСПАК`(034700).

`ГАСИПР` проверяет: поле АН = `(ДВРОС.значение48 >> 17) & 0xFFFFF`; если ≠0 —
`АНДВР`, `ДМА` (§5.5), затем границы относительно `АЗАЯВК`, кратность 8,
неравенство `A(ТВЗП)`, и наконец `АКТЗ` в слове 7.

### 7.3. Две проверки в `ВЫППВВ` **[Л][Н]**

Дословно (032514–032522):

```
СЧП 5(АДР)          ; ДР
СЧМР                ; ACC = тег16 << 32
СДА 64+34           ; вправо на 34  → тег16 >> 2
И =В'1777'
УИ НУС              ; НУС := ACC
СДА 64-1            ; влево на 1
УИ НСВС             ; НСВС := НУС<<1
ПО ОШДВР2           ; ОШИБКА, если НУС == 0          ← проверка 1

СЧП 4(АДР)          ; СПУ
СДА 64+38           ; ACC = СПУ >> 38
СЧИМ НУС            ; PUSH(СПУ>>38); ACC := НУС
НТЖ (S)             ; POP; ACC = НУС ^ (СПУ>>38)
И =В'17'
ПЕ ОШДВР2           ; ОШИБКА, если ≠ 0               ← проверка 2
```

(`ПО`=026 — переход по нулю, `ПЕ`=027 — по не-нулю.)

Итого: **НУС ≠ 0** и **младшие 4 разряда НУС совпадают с разр.39–42 СПУ**.
В наблюдённой заявке `СПУ>>38 = 0`, поэтому `НУС` обязан быть кратен 16 —
чему `0120` удовлетворяет, а `0121` уже нет. Это и отбраковало гипотезу
«НУС = база + номер устройства из НАПРУС».

> Ранее эта последовательность ошибочно трактовалась как протокол возврата
> адреса. `СЧИМ` (043) — не загрузка, а «протолкнуть и загрузить» (§3.4),
> поэтому `НТЖ (S)` снимает именно то, что было протолкнуто двумя командами
> ранее. Никакого адреса возврата здесь нет.

### 7.4. `ИНДБУД` и таблица `БУДКАН` **[Л][Н]**

`ИНДБУД` (035427) по НУС определяет канал и «заводит будильник»:

```
ЗП (S)              ; PUSH признак подзавода (ВЫППВВ передаёт =В'1')
МОДА ТУСЗ
СЧП (НУС)           ; ТУСЗ[НУС]
И =М32В'77'         ; КАНАЛ — разр.33–38
СЧИМ ВОЗВ / ЗП (S)
УИА БУДКАН-КОНБУД(Ц)
ИЩИКАН: МОДА БУДКАН ; СЧ КОНБУД-БУДКАН(Ц) ; И =М32В'77' ; НТЖ -2(S)
        ПО ВЗЯЛК    ; нашли канал
        ЦИКЛ ИЩИКАН(Ц)
```

**`БУДКАН`** (031772…032015, `КОНБУД`=032016) — **20 записей**, «будильник
каналов». Формат (по заголовку таблицы в исходнике):

| Разряды | Поле |
|---|---|
| 33–38 | номер канала (сверяется с ТУСЗ) |
| 11–20 | ВРЕМЯ ОЖИДАНИЯ |
| 1–10 | **ЧИСЛО АКТИВНЫХ ЗАЯВОК НА КАНАЛЕ (ЧАКБВВ)** |

Каналы в таблице: `01 02 03 04 05 06 08 0A 0B 0C 0D 0F 1C 1D 20 25 24 22 21 23`
(шестнадцатерично). Канал МД **0x22** стоит по индексу 17 — и поиск в прогоне
завершается ровно за 18 итераций **[Н]**, что независимо подтверждает
`НУС = 0120`.

Вернувшись, `ВЫППВВ` делает:

```
И =В'1777'          ; ЧАКБВВ
ПО ОШД12            ; "НУС В ТУС НЕВЕРЕН" — если счётчик НУЛЕВОЙ
СЧ (Ц) ; ВЧ =В'1' ; ЗП (Ц)     ; ЧАКБВВ = ЧАКБВВ - 1
```

### 7.5. Как возобновляется ждущая задача **[Н][Л]**

Выдав обмен, задача паркуется в `ЖДИПР` (032332) — это **чистое ожидание
прерывания**, не семафор и не опрос состояния заявки:

```
ЖДИПР  РЕГ '140'   ГАШУ СКП
       VТМ 3                  ← гасит PSW_INTR_DISABLE: прерывания разрешены
       РЖА 7
       ПБ ЖДИПР               ← вечный цикл, выйти можно только по прерыванию
```

Возврат из прерывания (`ВЫХПР`, 032315) восстанавливает регистры и делает
`ВЫПР (3)` — то есть возвращается **в прерванную точку**, обратно в цикл
`ЖДИПР`. Пробуждение устроено иначе, через `АНАЛИЗ`:

```
ОБРПРЕ  32313  УИА АНАЛИЗ(13)        M13 := 032327 — точка возврата обработчика
ППВВ    32630  ПБ (13)               выход обработчика → АНАЛИЗ
АНАЛИЗ  32327  ПО ВЫХПР   БВВ НЕТ    ← СМ=0: заявки нет, обычный возврат
               ЗП СМ1  АДРЕС ПОЛУЧ ЗАЯВКИ
ВЫХПР   32321  СЧ СМ1                возобновляемый код получает адрес в СМ
        32322  ВЫПР (3)
```

То есть обработчик обязан выйти с **адресом завершённой заявки в сумматоре**;
тогда `АНАЛИЗ` кладёт его в `СМ1`, и задача просыпается, получив заявку.

**Почему это не срабатывает.** `ППВВ` уходит ветвью `НЕТБВВ` (032610) по
проверке в 032601 — после цикла `ЦПБ` (032574-032600, «ПОИСК СВС, ВЫДАВШ.
БОЛЬШЕ ЗАЯВОК»), опирающегося на счётчики обменов `КОБМ` (032035). Завершённая
заявка не подключается к `ТВЗП[НСВС]`/`КОБМ`, как обещает заголовок `ППВВ`
(«ИСКЛЮЧ ЗАЯВКИ ИЗ ДВР, ПОДКЛЮЧЕНИЕ ЕЕ В ТВЗП[НСВС]»), поэтому отдавать
задаче нечего, СМ остаётся нулевым, и `АНАЛИЗ` делает обычный возврат в
`ЖДИПР` **[?]**.

#### 7.5.1. Запрос ПВВ — уровень, а не импульс **[Н]**

Отдельная ошибка эмулятора, найденная здесь же. Канал взводил `GRVP_INTR_IOM`
и никогда не гасил, а АДАП его не гасит тоже: во всём модуле **одна** команда
`РЕГ '47'`, и та относится к таймеру («ГАШУ ВРЕМ ПРЕР»); ни `ППВВ`, ни
`ГАСИПР` (он гасит *заявку*, а не прерывание) к РВП не обращаются.

Результат: обработчик `ППВВ` входил **164 680 раз** на одну заявку, попутно
затирая регистр 13 и ломая протокол возврата.

Гасить разряд при приёме прерывания нельзя — `ОБРПРЕ` читает РВП
(`РЕГ '247'`) уже внутри обработчика, чтобы выбрать ветвь, и без разряда до
`ППВВ` просто не доходит (проверено: `ППВВ` = 0). Правильная модель —
**уровень**: запрос держится, пока голова очереди ответов (`iom->SQA`,
ДВРПВВ) непуста, и снимается, когда АДАП её обнулил. Реализовано как
`iom_update_intr()`, вызываемая перед проверкой `ГРВП & ГРМ`.
После исправления `ППВВ` = 2, `ГАСИПР` = 2, `ВЫППВВ` = 2.

### 7.6. Пробуждение через межпроцессорное прерывание **[Н][Л]**

Разгадка §7.5: завершённую заявку задаче отдаёт **не** обработчик ПВВ, а
отдельное **межпроцессорное прерывание**, которое ПВВ-обработчик посылает
владельцу заявки — в однопроцессорной конфигурации самому себе.

```
ППВВ  32477  СЧСНХ ТВЗП(НСВС)          подцепил заявку в ТВЗП своего СВС
      32502  ДАЙ ЕСВС                  ЕСВС>>НСВС — разряд своего СВС
      32504  ИЛИ ПРЕР ; ЗП ПРЕР        "ЕМУ ПОШЛЮ ПРЕР"
      32610  СЧМ ПРЕР ; РЕГ '50'       "ВСЕХ ПРЕРВУ"
             ↓
ОБРПРЕ       НЕД(ГРВП&ГРМ) → ПБ ПРКЛПР-41(14)
ПРКЛПР 32306 УИА АНАЛИЗ-4(13) ; ПБ ПРСВС     ← ГРВП разр.8 = GRVP_REQUEST
ПРСВС  30020 … достаёт заявку, СМ := её адрес
АНАЛИЗ 32327 ЗП СМ1 ; ВЫХПР ; ВЫПР (3)  → задача просыпается в КНЦОБМ
```

Отображение разрядов ГРВП на входы `ПРКЛПР` (выведено из `НЕД`:
`n = svs_highest_bit`, переход `ПРКЛПР-41+n`, то есть вход = 41−n от разряда):

| n | разр. | ГРВП | вход |
|---|---|---|---|
| 41 | 8 | `GRVP_REQUEST` 0200 | **ПРСВС** |
| 42 | 7 | `GRVP_RESPONSE` 0100 | СТ102 «ОТВЕТ ОТ ПРОЦЕССОРОВ» |
| 43 | 6 | `GRVP_IOM_FAIL` 0040 | АВСВС «АВАРИЯ СВС» |
| 44 | 5 | `GRVP_RAM_FAIL` 0020 | СТ102 |
| 45 | 4 | `GRVP_TIMER` 0010 | ПРВРЕМ |
| 46 | 3 | `GRVP_INTR_IOM` 0004 | ПРПВВ |

Каждая метка совпадает по смыслу со своим разрядом — отображение подтверждено.

**Две ошибки эмулятора, мешавшие этому.**

1. `РЕГ '50'` записывал только `cpu->PP` и никого не прерывал (ветвь `else`
   уводила вызов в `iom_service_tvzp` — остаток пути `ОТДАЮЗ`). Теперь команда
   взводит **ПОП** по маске адресуемых процессоров (разр.39-42).
2. Взводить `GRVP_REQUEST` напрямую бесполезно: `cpu_one_instr` после **каждой**
   команды пересчитывает этот разряд как `(ПОП & РКП)`, так что прямая запись
   стирается на следующей же команде. Отсюда и требование: **разряд процессора
   в РКП обязан совпадать с `NSVS`** (СВС k — разряд 42−k). Для СВС 1 это
   `d RKP 1020000000000000`, а не `1040000000000000` (СВС 0).

## 8. Текущее состояние

**РАСПАК достигнут.** Полная цепочка проходит без единой ошибки:

```
ФОРБВВ → ЛНУТУС/ЛОКОБ (ЛУ 031 → НУС 0121) → ВКЛТОЧ → НУСЕС → ДИСПАК → ТЕСОБМ
  → ЧАКБВВ+1 → РЕГ '50' → канал: обмен → ДВРПВВ + ГРВП разр.3
  → ППВВ → ГАСИПР → АКТИВ → ВЫППВВ → ИНДБУД → ТВЗП[НСВС] + ПРЕР
  → РЕГ '50' → ПРСВС → АНАЛИЗ → ВЫПР(3) → КНЦОБМ → ВОСМД → РАСПАК
```

| Точка | Срабатываний |
|---|---|
| `ТЕСОБМ` 034311 / `ЧАКБВВ+1` 034316 | 2 / 2 |
| `ППВВ` 032334 / `ГАСИПР` 032400 / `АКТИВ` 032410 | 2 / 2 / 2 |
| `ВЫППВВ` 032514 / `ИНДБУД` 035427 | 2 / 4 |

| `ВОСМД` 034735 / **`РАСПАК` 034700** | 2 / **2** |
| `ОШДВР2` / `ОШД12` / `ОШДВР` / `СТ115` / `СТ100` | 0 / 0 / 0 / 0 / 0 |

Обмен выполняется по правильным параметрам:

```
iom0 --- обмен: устр=1 заявка@31100 ЧТ зона=511 буфер=42016
```

**Следующая преграда — уже за РАСПАК-ом.** Прогон завершается остановом

```
Останов, PC: 31520 (стоп 101)
СТ101   НОП   ,   ****** КЧ ПРИ ВОССТАНОВЛЕНИИ ЛИСТА
```

то есть `РАСПАК` отработал, лист распакован, но **контрольная сумма не сошлась**.

## 9. Открытые вопросы и упрощения в эмуляторе

1. **ДРУ (слово 6)** — назначение разрядов не установлено; пишется 0 **[?]**.
2. **Тип ёмкости устройства** должен читаться из `ТУСЗ[НУС]` и задавать
   масштаб зоны (§5.4); сейчас делитель 2 зашит в `iom_xfer_zaiavka` **[?]**.
3. **ТВЗП (031270)** — адрес зашит константой `IOM_TVZP`; команды регистрации
   для неё не наблюдалось, в отличие от УТ/ТОЧ/ОТВ (§4.2).
4. **Контроль тега (КЧ)** отключён намертво в `svs_mmu.c`
   (`if (0 && tag_check && …)`), так как загрузчик метит все слова 035/036.
5. **Цепочка из нескольких одновременных завершений** через ТОЧ не реализована:
   канал связывает с ДВРПВВ ровно одну заявку.
6. **Многопроцессорность** (`RKP` на cpu1) не реализована в эмуляторе.
7. **Контрольная сумма распакованного листа** не сходится (`СТ101`) — текущая
   преграда (§8). Протокол ПВВ здесь уже ни при чём.

## 10. Воспроизведение

Единственный правильный стенд — `SVS/dispak.ini`; самодельные мини-скрипты
вводят в заблуждение и использоваться не должны.

```sh
cd SVS && ./runsim.sh                # прогон со сторожем размера трассы (§11.3)
#   ./runsim.sh dispak.ini 2 300     # ini, лимит в ГБ, таймаут в секундах
grep -c '^cpu0 34700 ' dispak.trace  # достигнут ли РАСПАК
grep    'обмен:'       dispak.trace  # параметры заявки, как их увидел канал
```

Существенные строки `dispak.ini`:

| Строка | Зачем |
|---|---|
| `load adap.b6` | загрузить АДАП |
| `attach DISK1 …/svs2053.bin` | системный диск на канал 0, устройство 1 |
| `d RKP 1040000000000000` | один процессор (cpu0) и один ПВВ |
| `d 2 5000000` | слово пульта 2: номер канала для МД/МБ; без него СТОП 40114 |
| `d NSVS 1` | номер СВС работающей машины; при 0 диск «не наш» и АДАП уходит в `ОТДАЮЗ` (§5.3.2) |
| `d 30115 0030000000000200` | `НАПРУС` — логический номер устройства 031 → НУС 0121 → МД, устройство 1 (§5.3.1) |
| **`d RPS3 0017001600150014`** | **приписка страниц 12–15 на себя — см. §11.1** |
| `d 7 7777000000000000` | приписка стека |
| `d M7 30000`, `go 30036` | точка входа ВЫЗОС |

Кроме загрузки и конфигурации, в `dispak.ini` оставлены **диагностические точки
останова** — это рабочий стенд, а не «чистая» загрузка:

| Точка | Что смотрим |
|---|---|
| `br 33543` | ранняя контрольная точка; `e ACC`, `e rmr` |
| `br 32334` | вход `ППВВ` — обработка завершения началась |
| `br 35427` | вход `ИНДБУД`; `e 30320` (ТУСЗ[0120]), `e 30500` (ТУС[0120]), `e 32013` (БУДКАН[0x22]) |

Чтобы увидеть таблицы устройств целиком (а не их пустые головы, §11.2),
на точке `35427` вместо трёх отдельных `e` нужно смотреть диапазоны:
`e 30200-30357` и `e 30360-30537`.

## 11. Ловушки, стоившие больше всего времени

### 11.1. `ПЕРЕП` затирает таблицы через неприписанную страницу **[Н]**

Цикл `ПЕРЕП` (036034, 3072 итерации) копирует АДАП **сам в себя**: читает с
включённой припиской (`VТМ 1024`), пишет с выключенной (`VТМ 1027`). Если
СТЛБ для страниц 12–15 не настроен, чтение идёт с **физической страницы 0**
(умолчание `va_to_pa`), и цикл аккуратно забивает нулями уже загруженные
`ТУС`/`ТУСЗ`/`ТУСМД`. Симптом: таблицы, заведомо непустые в `adap.b6`,
в прогоне читаются нулями.

Лечится строкой `d RPS3 0017001600150014` (страницы 14,15,16,17₈ = 12–15).

### 11.2. Пустые головы таблиц вводят в заблуждение **[Н]**

`ТУСЗ`(030200) и `ТУС`(030360) начинаются с блока класса 0, который в этой
конфигурации пуст. Проверка «первых двух слов» показывает нули и создаёт
ложное впечатление, что таблица не заполнена. Смотреть надо **весь** диапазон
(`e 30200-30357`, `e 30360-30537`).

### 11.3. Незавершающийся `go` и гигабайтная трасса **[Н]**

`set cpu0 itrace` пишет ~3 МБ/с. Голый `go` с точкой останова, до которой АДАП
в данной конфигурации не доходит, не завершается никогда — за четверть часа
трасса вырастает до **десятков гигабайт** (наблюдалось 47 ГБ). Хуже того,
удаление файла не возвращает место, пока его держит открытым хоть один
читающий процесс (`grep` по трассе).

Меры:

- прогонять через `./runsim.sh [ini] [лимит-ГБ] [таймаут-с]` — сторож снимает
  симулятор при превышении лимита (по умолчанию 2 ГБ / 300 с);
- вместо голого `go` использовать ограниченный `step N` — он тоже
  останавливается на точке останова, но не может идти вечно;
- после разбора удалять `dispak.trace` (в начале `dispak.ini` есть
  `! rm -f dispak.trace`, но он срабатывает только на следующем прогоне).

### 11.4. Буферизация вывода симулятора

При перенаправлении в `head`/`tail` вывод буферизуется целиком, и нормальный
прогон выглядит как зависший (не видно ни строки до самого конца).
Перенаправлять надо в файл. Кроме того, `go` без достижимой точки останова
не завершается никогда — ограничивать `step N`.

### 11.5. Псевдонимы регистров **[Л]**

Один регистр обычно имеет несколько имён; это норма, а не ошибка чтения:

| Рег. | Имена |
|---|---|
| 1 | НСВС |
| 2 | АЗАЯВ, R |
| 3 | НШГ, НР, **НУС** |
| 4 | ТИП |
| 5 | АДР |
| 6 | R1, СЛЕД |
| 7 | БАЗА |
| 14 | ВОЗВ, Ц, М16 |
| 15 | S, М17 — **он же указатель аппаратного стека** (017₈) |

Отдельного имени `М7` нет — используется `(БАЗА)`.
