# ПВВ — процессор ввода-вывода СВС: форматы заявок, режимы работы, взаимодействие с АДАП

Документ описывает протокол между центральным процессором СВС (программа **АДАП**)
и канальным процессором **ПВВ** в том виде, в каком он восстановлен по исходному
тексту АДАП-а и по прогонам эмулятора. На этот документ ссылаются комментарии в
`svs_iom.c` (`§5.2`, `§5.4`, `§5.6`) и `svs_disk.c` (`§5`).

## 1. Статус сведений

Протокол ПВВ восстанавливался по коду и трассам; позже нашлась заводская
документация (`IOM_instruction_set.md`, раздел 4 из №10.170.002 ТОП), сверка с
ней — в §7Б. Где документ и реконструкция расходятся, прав документ. Каждое
утверждение снабжено пометкой о том, чем оно подтверждено:

| Пометка | Что означает |
|---|---|
| **[К]** | Код эмулятора: реализация команды в `svs_cpu.c` / `svs_mmu.c`. Достоверно по построению. |
| **[Н]** | Наблюдение в прогоне `dispak.ini` (трасса `dispak.trace`, дампы памяти). Достоверно для текущей конфигурации. |
| **[Л]** | Листинг компиляции `adapcmp.b6` (совпадает побайтно с настоящим `adap.b6`). Достоверно как намерение АДАП-а. |
| **[Д]** | Заводская документация ПВВ №10.170.002 ТОП (`IOM_instruction_set.md`). Первичный источник, старше любых наших реконструкций. |
| **[?]** | Вывод/догадка, прямо не проверенная. |

Источники: `adapcmp.b6` (реконструированный исходник АДАП-а),
`besm6.github.io/sources/dispak-svs/adap.txt` (компилированный листинг настоящего
АДАП-а — та же логика по другим адресам), `генс.bemsh` (см. §7A),
`IOM_instruction_set.md` (заводское описание, см. §7Б), `svs_iom.c`, `svs_disk.c`.

## 2. Действующие лица

- **СВС** — центральный процессор. Исполняет **АДАП** — резидентную программу
  диспетчера ввода-вывода, занимающую страницы 12–15 (физ. 030000–037777).
- **ПВВ** — процессор ввода-вывода (канал). В реальной машине — отдельный
  процессор со своей памятью; в эмуляторе — `svs_iom.c`, работающий прямо по
  физической памяти СВС.
- Связь двусторонняя и асинхронная: СВС → ПВВ через **командное слово БАК**
  плюс «звонок в дверь» (`РЕГ '50'`); ПВВ → СВС через **внешнее прерывание**
  (ГРВП разр.3) плюс структуры в памяти.

## 3. Представление данных

### 3.1. Ячейка памяти: полноразрядное слово **[К]**

Ячейка `memory[]` хранит **полноразрядное 64-разрядное слово**. Обычные
команды видят только его старшие 48 разрядов; младшие 16 доступны лишь
полноразрядным командам, и только через РМР:

```
memory[a] = (значение48 << 16) | мл16
```

`мл16` — это просто **младшие 16 разрядов полного слова**, и ничего больше.
**Тегом они не являются.** Аппаратный тег (`TAG_INSN48`=035,
`TAG_NUMBER48`=036, `TAG_BITSET`=020) лежит отдельно, в массиве `tag[]`,
и в самом слове его нет.

Граница между «значением48» и «мл16» — это только про то, какая команда какую
часть слова видит; поля заявок через неё спокойно проходят. Например НАМ слова
ДО занимает разр.1–20 полного слова, то есть все 16 разрядов `мл16` плюс
четыре младших разряда `значения48` (§5.4).

На этом стоит весь протокол: номера зон, адреса и номера устройств АДАП
передаёт в младших разрядах полного слова, а данные обмена — в старших.

### 3.2. Полноразрядные команды **[К]**

| Команда | Код | Действие |
|---|---|---|
| `СЧП` | 033 | `ACC = значение48`, `РМР = мл16 << 32` |
| `СОП` | 046 (ф.2) | то же |
| `СЧМР` | 031 | `ACC = РМР` — прочитать сохранённые `мл16` |
| `ЗПП` | 032 | записать `(ACC<<16) \| ((РМР>>32) & 0xFFFF)` |

Типичная связка «достать младшие разряды»: `СЧП x; СЧМР; СДА 64+n; И =маска`.
После `СЧП` они стоят в разр.33–48 сумматора, поэтому сдвиг вправо на `32+k`
даёт `мл16 >> k`.

### 3.3. Сдвиг `СДА` **[К]**

`n = (Aex & 0177) - 64`; **положительное `n` — сдвиг вправо**, отрицательное —
влево. То есть `СДА 64+38` — вправо на 38, `СДА 64-1` — влево на 1.

### 3.4. Аппаратный стек: регистр 017 **[К]**

Регистр `М17` (017₈ = 15) — указатель стека; операнд вида `(S)`/`(17)`
автоинкрементируется при записи и автодекрементируется при чтении.

| Команда | Код | Действие |
|---|---|---|
| `СЧИМ` | 043 | **PUSH ACC**, затем `ACC := M[операнд]` |
| `ЗП (S)` | 000 | PUSH ACC |
| `НТЖ (S)` | 012 | **POP**, `ACC ^= снятое` |
| `УИМ` | 041 | POP в регистр |

`СЧИМ X` проталкивает текущий ACC в стек и загружает X. Пара
`СЧИМ X; НТЖ (S)` вычисляет `X ^ (то, что было в ACC)`.
Именно она реализует вторую проверку в `ВЫППВВ` (§7.3).

### 3.5. Приписка страниц **[К]**

`УИА`/`vtm` с регистром 0 в режиме супервизора попутно пишет разряды ССП из
`addr & (PSW_INTR_DISABLE|PSW_MMAP_DISABLE|PSW_PROT_DISABLE)`. Отсюда идиома
АДАП-а: `VТМ 1024` — приписка **включена**, `VТМ 1027` — **выключена**.
Разряды ССП (восьмерично): `MMAP_DISABLE`=1, `PROT_DISABLE`=2,
`CHECK_HALT`=10, `INTR_DISABLE`=2000.

### 3.6. Макрос `ДАЙМА` **[Л]**

```
ДАЙМА:  СЧМР ; ПО skip ; СДА 64+32 ; ДМА ПМА
```

Извлекает указатель, закодированный в `мл16`: адрес хранится как
`z + A(ПМА)`, а `ДАЙМА` возвращает `мл16 - A(ПМА) = z`. `ПМА` = 032102.
В `svs_iom.c` тому же служит `IOM_DAIMA(v) = v & 077777`.

## 4. Инициализация: командное слово БАК и регистрация таблиц

### 4.1. Как СВС отдаёт команду каналу **[Л][Н]**

АДАП строит командное слово (adap.bemsh:2960-2965) как
«адрес блока `БАКПВВ` с точки зрения ПВВ **ИЛИ** КОП», затем `СДА 64+16; ЗПП`.
Из-за сдвига вправо на 16 **значащие 48 разрядов оказываются в младшей
половине** 64-разрядной ячейки — противоположно словам данных (§3.1).

Слово кладётся в `СТБАК` (0100₈, поле `iom->HA`), после чего следует звонок:
`СЧ ЕПВВ; РЕГ '50'`.

Формат командного слова:

```
разр. 1..36   адрес 2-словного блока БАКПВВ (физический; макрос ДФАПВВ
              прибавил базу АДРЕС = 030100). Здесь же флаги СЕМБИТ (разр.17)
              и ПОБ (разр.21).
разр. 37..44  КОП — код операции (база М36, младший разряд = разр.37)
```

### 4.2. Коды КОП **[Н]**

| КОП | Смысл | Куда попадает |
|---|---|---|
| 004 | инициализация БАК (указатель на БАКПВВ) | обрабатывается через `СТБАК` |
| 005 | регистрация **таблицы устройств** | `iom->UTA`; наблюдалось `УТ@030360` = **ТУС** |
| 006 | регистрация **таблицы очередей** | `iom->IOQA`; наблюдалось `ТОЧ@030540` = **ТОЧ** |
| 007 | регистрация **таблицы ответов** | `iom->SQA`; наблюдалось `ОТВ@031350` = **ДВРПВВ** |
| 015 | управляющая команда без адреса | запускает обслуживание ЕСВС/ТВЗП |
| 016 | `ПУСКОБ` — пуск обмена по очереди ТОЧ | `iom_pusk_obmen()` |

> Адреса этих трёх таблиц **не должны быть зашиты в эмуляторе** — канал узнаёт
> их от самого АДАП-а командами 005/006/007. Исключение — `ТВЗП` (031270):
> для неё команды регистрации не наблюдалось, поэтому адрес пока константа
> `IOM_TVZP` (см. §9.3).

## 5. Обмен

### 5.1. Общая схема

```
       АДАП (СВС)                                   ПВВ (канал)
  ФОРБВВ: собрать заявку  ──┐
  ВКЛТОЧ: выбрать путь      │
     НУС=0 → ОТДАЮЗ ────────┼──► ТВЗП[НСВС] + СЕМБИТ, звонок РЕГ '50'
     НУС≠0 → НУСЕС ─────────┴──► ТОЧ[2·НУС] (НОЧ/КОЧ), затем ПУСКОБ
                                        │
                                        ▼
                                  выполнить обмен с устройством
                                  записать ДР/ДРУ (сл.5/6)
                                  взвести АКТЗ (сл.7)
                                  связать заявку в ДВРПВВ
                                  ГРВП разр.3 (GRVP_INTR_IOM)
                                        │
  Я501 ◄────────────────────────────────┘
  ОБРПРЕ → ПРПВВ → ППВВ → ГАСИПР → АКТИВ → ВЫППВВ → ИНДБУД → РАСПАК
```

### 5.2. Блок заявки (БВВ) и очереди ТОЧ

Заявка — **8-словный блок, выровненный на 8** **[Л][Н]**. В текущей
конфигурации единственная заявка лежит по `А(ЗАЯВКИ)` = **031100**
(из `АЗАЯВК`@031601).

| Слово | Имя | Содержимое |
|---|---|---|
| 0 | — | связь со следующей заявкой (извлекается `ДАЙМА`, §3.6) |
| 1 | — | *(не наблюдалось)* |
| 2 | **ДО** | дескриптор данных: **НАМ** — адрес массива в ОП (разр.1–20, §7Б.7), **РАЗМ** — размер в словах (разр.22–41, §7Б.8) |
| 3 | **СО** | управление обменом; разр.48 = чтение (ТЕГ48) |
| 4 | **СПУ** | физический адрес зоны; см. §5.4 |
| 5 | **ДР** | ответ устройства (заполняет канал); в `мл16` — НУС, см. §5.5 |
| 6 | **ДРУ** | ответ устройства, продолжение |
| 7 | — | признаки; **АКТЗ** = М20В'1' = 04000000; направление+устройство в разр.42–47 (`СБР =М39В'7'М7В'7'`); номер драйвера; НЗАД |

**ТОЧ** — таблица очередей, **по 2 слова на устройство**: `НОЧ` (начало) и
`КОЧ` (конец) списка заявок. Индекс — **2·НУС** **[Л]** (КАНСОВ,
adap.bemsh:2153). Заявки связаны в список через слово 0.

В указателях старшие разряды несут признаки, в частности **СЕМБИТ**
(разр.17 = 0200000) — семафор занятости; значащий адрес выделяется
маской `& 077777`.

### 5.3. Таблицы устройств ТУСЗ / ТУС и номер НУС **[Н]**

Это центральная структура. Её устройство (дамп в точке `ИНДБУД`, см. §10):

```
ТУСЗ = 030200, 112 слов (0160₈): 030200 … 030357
ТУС  = 030360, 112 слов (0160₈): 030360 … 030537
```

Таблицы **параллельны**: запись `ТУСЗ[i]` и `ТУС[i]` описывают одно устройство,
расстояние между ними ровно 0160₈. Каждая разбита на **7 блоков по 16 записей**
— по блоку на класс устройства:

| Смещение | Адрес в ТУС | Адрес в ТУСЗ | Класс | КАНАЛ (разр.33–38 ТУСЗ) |
|---|---|---|---|---|
| 000 | 030360 | 030200 | — | (частично заполнен) |
| 020 | 030400 | 030220 | 1 | 0x01 |
| 040 | 030420 | 030240 | 2 | 0x0C |
| 060 | 030440 | 030260 | 3 | 0x0D |
| 100 | 030460 | 030300 | 4 | 0x20 |
| **120** | **030500** | **030320** | **5 — МД (диск)** | **0x22** |
| 140 | 030520 | 030340 | 6 | 0x24 |

Блок МД по смещению 0120 — это и есть символ **ТУСМД** (030500) из исходника;
его начальное значение в `adap.b6` содержит `М32Х'22'`, то есть номер канала
0x22 задан на этапе компиляции **[Л]**.

**Формат записи ТУС** (после обработки, §5.3.1): старшее поле — **кольцевая
ссылка** на следующую запись блока:

```
ссылка = (смещение_следующей_записи_от_ТУС) * 4 + 2
```

Например `ТУС[0120]`=030500 содержит `0506…`: следующая запись имеет смещение
0121, `0121*4+2 = 0506`. Последняя запись блока (030517) ссылается обратно на
первую (`0502`) — кольцо из 16 записей.

**Номер устройства НУС** — это **индекс записи в ТУС/ТУСЗ**:

```
НУС = смещение_блока_класса + номер_устройства_внутри_класса
```

Для системного диска (класс МД) базовое смещение — **0120₈**. Это подтверждено
дважды **[Н]**: обе проверки в `ВЫППВВ` проходят (§7.3), и `ИНДБУД` находит
канал 0x22 в `БУДКАН` ровно за 18 итераций — по индексу 17, где `0x22` и стоит
(§7.4).

> Младшие 4 разряда НУС — номер устройства внутри класса; `ВЫППВВ` сверяет их
> с разрядами 39–42 слова СПУ, которое строит сам АДАП (§7.3). Поэтому канал
> обязан брать это поле **из заявки**.

#### 5.3.1. Как АДАП получает НУС: ЛНУТУС → ЛОКОБ → ТОУ **[Н][Л]**

НУС не задаётся снаружи — АДАП вычисляет его из **логического номера
устройства (ЛУ)**:

```
ФОРБВВ: СЧИ НУС ; ПВ ЛНУТУС     (34615)   ЛУ на входе в сумматоре
ЛНУТУС (34413) → ЛОКОБ (34107) → таблица ТОУ (31465)
```

**ТОУ** — ТАБЛИЦА ОБЩИХ УСТРОЙСТВ, индексируется типом устройства (`ТИП`;
`МДТИП ЭКВ 0`, поэтому МД — нулевая запись, 031465). Формат записи:

```
ТОУ[МД] = 0003006000400120   М35В'06' М25В'30' М15В'04' В'120'      МД 30-33
            разр.26-31 = 030   первый логический номер
            разр.16-18 = 4     сколько устройств
            разр.1-7   = 0120  база блока в ТУС
```

То есть МД занимает **логические номера 030-033**, отображаемые на индексы
ТУС **0120-0123**. `ЛОКОБ` линейно обходит диапазоны ТОУ и возвращает
`НУС = база + (ЛУ − первый)`. Если ЛУ ни в один диапазон не попал, НУС=0, и
`ВКЛТОЧ` уходит ветвью `ОТДАЮЗ` (§6).

Соответствующие записи МД в **ТЛУ** (таблица ЛОКАЛЬНЫХ устройств) нулевые:
диск — общее устройство.

**Кодировка ЛУ в НАПРУС.** ФОРБВВ собирает логический номер командой
`СБР =М39В'7'М7В'7'` (34607), то есть из разрядов **42,41,40 и 10,9,8**
(старший→младший). Поэтому:

| ЛУ | НАПРУС |
|---|---|
| 030 | `0030000000000000` |
| **031** | **`0030000000000200`** |
| 032 | `0030000000000400` |
| 033 | `0030000000000600` |

Значение, не затрагивающее ни одного из этих разрядов, даёт нулевой ЛУ, и
заявка уходит в `ОТДАЮЗ`.

#### 5.3.2. Маска СВС-владельца и номер машины **[Н][Л]**

Пройдя `ВКЛТОЧ`→`НУСЕС`, заявка попадает в `ДИСПАК` (034301), где проверяется,
принадлежит ли устройство этой машине:

```
34301  МОДА ТУСЗ ; СЧП (НУС)
34302  ПО ОТДАЮЗ        ТУС НЕ ОПРЕДЕЛЕН        ← ТУСЗ[НУС] == 0
       СДА 64-26        разр.7-16 → позиция 33-42 (МАСКА СВС)
...
34305  СЧ ЕСВС ; СДА 64(НСВС) ; И (S)
34306  ПЕ ОТДАЮЗ        НЕДОСТУПНО ДЛЯ ОС       ← бит своего СВС стоит в маске
       ПБ ТЕСОБМ
```

`ЕСВС` (031567) = `0040000000000000` — единица в разр.42, сдвигаемая вправо на
`НСВС`. Маска владельца для МД (разр.7-16 записи ТУСЗ) равна **01177**:

| НСВС | разряд | бит маски | итог |
|---|---|---|---|
| 0 | 42 | 1 | `ОТДАЮЗ` — диском не владеет |
| **1** | 41 | **0** | **`ТЕСОБМ`** — владеет |
| 2 | 40 | 0 | `ТЕСОБМ` — владеет |
| 3 | 39 | 1 | `ОТДАЮЗ` |

Номер машины АДАП читает командой `РЕГ '250'` (позиционный код: номер
кодируется НУЛЁМ в своей позиции среди единиц). В эмуляторе он берётся из
**`cpu_svs_number`** — регистр `NSVS`, задаётся из .ini как `d NSVS 1`.
Эмулятор исполняет одну машину за раз, но её номер выбирается.

#### 5.3.3. Учёт активных заявок: ЧАКБВВ **[Л][Н]**

На локальном пути АДАП сам увеличивает счётчик активных заявок канала
(разр.1-10 записи `БУДКАН`) перед выдачей команды:

```
34316  ИЛИ (Ц)
       СЛЦ =В'1'     УВЕЛИЧИЛ СЧ-К АКТИВНЫХ БВВ
34317  ЗП (Ц)
       СЧПР БАКПВВ
```

`Ц` указывает на запись БУДКАН, найденную вызовом `ИНДБУД` двумя командами
ранее. При завершении `ВЫППВВ` уменьшает этот счётчик (032526) и требует,
чтобы он был ненулевым, иначе `ОШД12`. Поэтому канал **не должен** вести этот
счётчик сам: на своём пути АДАП делает это без посторонней помощи.

#### 5.3.4. РОСТУС — формирование ссылок **[Н][Л]**

Подпрограмма `РОСТУС` (036050, «ФОРМИР ССЫЛОК») **преобразует уже загруженную
ТУС на месте**: читает `ТУС[i]`, выделяет поле «СМЕСЬ» (`И =В'7'`), и
записывает обратно ссылку на следующую запись. Она **не** заполняет ТУС из
ТУСМД — ТУСМД есть часть ТУС. В прогоне выполняется 112 раз (по одной
итерации на запись), что ровно соответствует размеру таблицы.

Смотреть содержимое таблиц по адресам 030200/030360 бесполезно: это **пустые
головы** (блок класса 0), а содержимое начинается со смещения 020.

### 5.3.5. Классы устройств и маршрутизация обмена **[Н][Л]**

Блок класса k лежит в ТУС/ТУСЗ по смещению **k*16**, а НОМЕР КЛАССА записан в
младшем поле самой записи ТУС (проверено дампом):

| Класс | Метка | Адрес в ТУС | Смещение | Записей | Канал |
|---|---|---|---|---|---|
| 4 | `ТУСМБ` — магнитный барабан | 030460 | 0100 | 8 (МБ 00-07) | Х'20' |
| 5 | `ТУСМД` — магнитный диск | 030500 | 0120 | 16 | Х'22' |

Поэтому канал НЕ должен вычитать фиксированную базу: и класс, и номер
устройства внутри класса берутся из ТУС, адрес которой регистрирует команда
БАК КОП=005 в `iom->UTA` (`iom_tus_class()` в `svs_iom.c`):

```
класс    = младшее поле ТУС[НУС]
номер    = НУС - класс*16
```

Тот же номер класса идёт в НУС ответа ДР (`класс*16 + номер`), иначе ВЫППВВ
получит чужой НУС.

**Барабан (`svs_drum.c`) отличается от диска двумя вещами:**

1. **Никакой свёртки 4:3.** Диск сворачивает 1024 слова зоны в 768 слов памяти
   (D-слова плюс фрагменты S-слов в РМР), потому что этого ждёт РАСПАК.
   Барабан хранит слова один к одному.
2. **Теги сохраняются буквально.** Диск при чтении метит всё как команду, при
   записи ставит 035/036; барабан пишет и читает полное 64-разрядное слово
   `memory[]` вместе с `tag[]` без перевода.

Барабаны — чистые (scratch): образ заранее не нужен, файл создаётся пустым и
разреженным, незаписанная зона читается нулями. Деление номера зоны пополам —
свойство МД (тип ёмкости), к барабану не применяется.

### 5.4. Описатель обмена: ДО, СО, СПУ

Наблюдённая заявка **[Н]** (`iom0 --- обмен: устр=1 заявка@31100 ЧТ зона=511 буфер=42016`):

```
ДО  = 0000000000142016   (РМР 002360)
СО  = 5014000000000000
СПУ = 0001212000200000   (РМР 001222)
```

- **ДО** — два поля полного 64-разрядного слова: **НАМ** (начальный адрес
  массива, разр.1–20) и **РАЗМ** (размер в словах, разр.22–41). НАМ почти
  целиком лежит в младших 16 разрядах, как и номер зоны в СПУ, но на четыре
  разряда заходит в значение48 (§3.1), поэтому маска — `& 0xFFFFF`, а не
  `& 0xFFFF`. Наблюдалось `ДО=0000000000142000 (НАМ 0002360 РАЗМ 784)`:
  784 = `0o1420` — то же поле длины, что в константе `ДОМЛМД`@032140
  (`М22В'1420'`), а адрес — `02360`.
  Адрес **физический**: приписка к нему не применяется, канал работает с ОЗУ
  через коммутатор связи. Это самое дорогое исправление по заводскому
  документу — см. §7Б.7, а про РАЗМ — §7Б.8.
  Раскладка зоны: 16 служебных слов с базы и **768 слов данных с базы+16**
  (итого 784 = `0o1420`). При базе 02360 это 02400–03777 — ровно тот диапазон,
  который читает РАСПАК (034716: `УИА -767(3)`; 034717: `СЧ 3777(3)`), и он
  целиком помещается в одной странице.
- **СО** — направление и режим. В единственной наблюдённой заявке (чтение)
  установлены **разр.39, 40, 46, 48** — что совпадает с признаком «ТЕГ48 чтение
  = разр.39,40,46,48» из комментария `svs_iom.c`. Канал сейчас различает
  направление **только по разр.48** (`is_read = (so >> 47) & 1`); остальные три
  разряда не проверяются. Признак записи (по тому же комментарию — разр.39,40)
  **не наблюдался ни разу** **[?]**, поэтому на чём именно чтение и запись
  различимы — по одному разр.48 или по всей четвёрке — этими данными не
  устанавливается.
- **СПУ** — физический адрес зоны. Сам номер зоны канал берёт **не из
  значения48, а из младших 16 разрядов полного слова** (`memory[z+4] & 0xFFFF`
  = 001222) — это и есть «копия младших 16 разр. адреса в РМР». Зона удвоена,
  поэтому `зона = мл16 >> 1` = 0611 → 511₈.
  Множитель зависит от **типа ёмкости устройства**, который положено брать из
  `ТУСЗ[НУС]`; сейчас он не читается, а делитель 2 зашит **[?]** — см. §9.2.
- Разряды 39–42 значения48 СПУ — номер устройства внутри класса, сверяемый
  в `ВЫППВВ` (§7.3). В наблюдённой заявке это поле **равно 0**.

Зона на диске — 8 служебных слов + 1024 слова данных (768 D + 256 S), в
памяти — 776 упакованных слов. **Всё прочитанное с диска метится как КОМАНДА
(035).** Это существенно: тег переносится дальше сам — РАСПАК читает слово
через `СОП` («ЧТ ПОЛН С ТЕГОМ БЭСМ», mmu_load_with_tag кладёт тег в `TagR`) и
пишет через `ЗП`/`ЗПП` (`mmu_store64` берёт тег из `TagR`; `mmu_store` — из
ПКП/ПКЛ, которые `РЕГ '101'` оставляет нулевыми). Пометь данные числом (036) —
и распакованная «вызывалка» окажется данными, а переход на неё даст контроль
команды; пометь `TAG_BITSET` — и обычное чтение `СЧ` даст контроль числа.

#### 5.4.1. Свёртка зоны 4:3 и порядок групп **[Н]**

Зона на диске — 8 служебных слов и 1024 слова данных, в памяти — 776 слов
(16 служебных + 768 упакованных). Упакованное слово несёт D-слово в старших
48 разрядах и 16-разрядный фрагмент S-слова в РМР.

**РАСПАК распаковывает в два прохода** (проверено трассировкой):

| Проход | Что делает | Куда |
|---|---|---|
| `ЦИКР` (034710) | собирает РМР трёх подряд идущих упакованных слов в одно | 256 слов, 02000-02377 — **восстановленные S-слова** |
| `ОЧМЛ` (034716) | обнуляет РМР 768 слов на месте | 02400-03777 — **чистые D-слова** |

Отсюда два требования к раскладке:

1. **S-область — НАЧАЛО зоны:** `buf[8..263]`. Точка входа «вызывалки»
   (02000) — это первое S-слово.
2. **Группы кладутся в ОБРАТНОМ порядке.** `ЦИКР` читает упакованные слова
   сверху вниз (03777, 03776, …), а результат пишет снизу вверх (02000,
   02001, …). Значит верхняя тройка обязана нести первую логическую группу;
   иначе страница выходит перевёрнутой — в 02000 оказывается S[255].

После исправления первые слова распакованной страницы совпадают с образом
диска точно:

```
02000 = 0002 0101 0300 2023    рег 101 ; пб 2023
02001 = 0002 0237 0330 0200    рег 237 ; стоп 200
02002 = 0300 2001 0220 0000    пб 2001 ; мода
02003 = 0002 0247 0330 0201
```

### 5.5. Ответ канала: ДР, ДРУ, АКТЗ, ДВРПВВ

Завершив обмен, канал обязан сделать **четыре** вещи **[Н]** — пропуск любой
из них уводит АДАП в обработчик ошибки:

1. **ДР (сл.5)** — `значение48` = код завершения (0 — успех), `мл16` = `НУС << 2`.
   `ВЫППВВ` читает `НУС = (мл16 >> 2) & 01777`.
2. **ДРУ (сл.6)** — продолжение ответа. Назначение разрядов не установлено **[?]**;
   сейчас пишется 0, и `ВЫППВВ` это принимает.
3. **АКТЗ (сл.7)** — взвести признак «активная заявка» (М20В'1' = 04000000)
   в `значение48`. Без него `ГАСИПР` считает, что встретил заявку впервые,
   сам взводит АКТЗ и уходит на `ОШДВРО` (сброс канала).
4. **Связать заявку с ДВРПВВ** — головой очереди завершённых заявок,
   зарегистрированной командой КОП=007 (`iom->SQA`, наблюдалось 031350):

   ```
   значение48 = (z - ПВВ) << 17     где ПВВ = 030000
   мл16       = z + A(ПМА)          где A(ПМА) = 032102
   ```

   Смещение относительно `ПВВ` обязательно: `ГАСИПР` после выделения поля АН
   делает `ДМА` (= `ВЧ АДРЕС`), а `память[АДРЕС]` хранит `−ПВВ`, так что из
   `(z−ПВВ)` получается абсолютный `z`. Если положить туда голый `z`,
   на выходе будет `z+ПВВ`.

Затем канал поднимает внешнее прерывание: `ГРВП |= GRVP_INTR_IOM` (разр.3).

### 5.6. Сводка форматов командного слова

См. §4.1 (разряды) и §4.2 (таблица КОП). Ключевое отличие от слов данных:
у командного слова БАК значащие 48 разрядов лежат в **младшей** половине
64-разрядной ячейки, у слов данных — в **старшей**.

## 6. Два режима подачи заявки **[Л]**

`ВКЛТОЧ` (adap.bemsh) ветвится по НУС:

- **НУС = 0 → `ОТДАЮЗ`.** Заявка кладётся в `ТВЗП[НСВС]` с признаком `СЕМБИТ`
  (разр.17), после чего звонок `ДАЙ ЕСВС; РЕГ '50'`. Это путь «отдать заявку
  другой СВС» — короткий, в обход очередей ТОЧ.
- **НУС ≠ 0 → `НУСЕС`.** Заявка ставится в очередь `ТОЧ[2·НУС]` (НОЧ/КОЧ), и
  обмен запускается командой `ПУСКОБ` (КОП=016).

В текущей конфигурации `dispak.ini` системный диск приходит в `ВКЛТОЧ`
с **НУС = 0** и уходит по ветви `ОТДАЮЗ`; поэтому ТОЧ пуста, а `ПУСКОБ`
вхолостую. Это и есть корень оставшейся проблемы — см. §8.

## 7. Обработка завершения на стороне АДАП

### 7.1. Приём прерывания **[Л][К]**

АДАП сам ставит свои векторы (adapcmp.b6:1404-1407):
`СЧ ВНЕПР; ЗП Я501` и `СЧ ВНУПР; ЗП Я500`. Вектор 0500 — внутреннее
прерывание (РПР), 0501 — внешнее (ГРВП). `ВНЕПР` = `ЗП СМ1; ПБ ОБРПРЕ`.

Разряды ГРВП: `PANEL_REQ`=0001, **`INTR_IOM`=0004**, `TIMER`=0010,
`REQUEST`=0200; наблюдавшаяся маска ГРМ = 0277.

Прерывание доставляется только при (`svs_cpu.c`):

```c
if (!iintr && !(RUU & RUU_RIGHT_INSTR) && !(M[PSW] & PSW_INTR_DISABLE)) …
```

то есть **при выключенном разряде `PSW_INTR_DISABLE` (2000₈)** и не на правой
команде слова. Если АДАП крутится с запретом прерываний, поднятый `INTR_IOM`
просто ждёт.

### 7.2. Диспетчеризация **[Л][Н]**

`ОБРПРЕ` (032275) читает ГРВП (`РЕГ '247'`) и ГРМ (`РЕГ '246'`), нормализует
(`НЕД`) и вычисляемым переходом уходит в таблицу из 6 входов `ПРКЛПР`:
`ПРСВС / СТ102 / АВСВС / СТ102 / ПРВРЕМ / ПРПВВ`. Разряду 3 соответствует
`ПРПВВ` → `ППВВ` (032334).

`ППВВ` начинается с `СЧСНХ ДВРПВВ; ЗППР ДВРОС` — то есть **ДВРОС (031347) есть
копия ДВРПВВ (031350)**. Канал обязан писать в ДВРПВВ; в ДВРОС писать
бесполезно, его перезапишут.

Далее: `ГАСИПР`(032400) → `АКТИВ`(032410) → `ППВВИН`(032423) →
`БЕЗОШБ`(032470) → `ВЫППВВ`(032514) → `ИНДБУД`(035427) → `РАСПАК`(034700).

`ГАСИПР` проверяет: поле АН = `(ДВРОС.значение48 >> 17) & 0xFFFFF`; если ≠0 —
`АНДВР`, `ДМА` (§5.5), затем границы относительно `АЗАЯВК`, кратность 8,
неравенство `A(ТВЗП)`, и наконец `АКТЗ` в слове 7.

### 7.3. Две проверки в `ВЫППВВ` **[Л][Н]**

Дословно (032514–032522):

```
СЧП 5(АДР)          ; ДР
СЧМР                ; ACC = мл16 << 32
СДА 64+34           ; вправо на 34  → мл16 >> 2
И =В'1777'
УИ НУС              ; НУС := ACC
СДА 64-1            ; влево на 1
УИ НСВС             ; НСВС := НУС<<1
ПО ОШДВР2           ; ОШИБКА, если НУС == 0          ← проверка 1

СЧП 4(АДР)          ; СПУ
СДА 64+38           ; ACC = СПУ >> 38
СЧИМ НУС            ; PUSH(СПУ>>38); ACC := НУС
НТЖ (S)             ; POP; ACC = НУС ^ (СПУ>>38)
И =В'17'
ПЕ ОШДВР2           ; ОШИБКА, если ≠ 0               ← проверка 2
```

(`ПО`=026 — переход по нулю, `ПЕ`=027 — по не-нулю.)

Итого: **НУС ≠ 0** и **младшие 4 разряда НУС совпадают с разр.39–42 СПУ**.
В наблюдённой заявке `СПУ>>38 = 0`, поэтому `НУС` обязан быть кратен 16 —
чему `0120` удовлетворяет, а `0121` уже нет. Это и отбраковало гипотезу
«НУС = база + номер устройства из НАПРУС».

> `СЧИМ` (043) — «протолкнуть и загрузить» (§3.4), поэтому `НТЖ (S)` снимает
> именно то, что протолкнуто двумя командами выше. Адреса возврата здесь нет.

### 7.4. `ИНДБУД` и таблица `БУДКАН` **[Л][Н]**

`ИНДБУД` (035427) по НУС определяет канал и «заводит будильник»:

```
ЗП (S)              ; PUSH признак подзавода (ВЫППВВ передаёт =В'1')
МОДА ТУСЗ
СЧП (НУС)           ; ТУСЗ[НУС]
И =М32В'77'         ; КАНАЛ — разр.33–38
СЧИМ ВОЗВ / ЗП (S)
УИА БУДКАН-КОНБУД(Ц)
ИЩИКАН: МОДА БУДКАН ; СЧ КОНБУД-БУДКАН(Ц) ; И =М32В'77' ; НТЖ -2(S)
        ПО ВЗЯЛК    ; нашли канал
        ЦИКЛ ИЩИКАН(Ц)
```

**`БУДКАН`** (031772…032015, `КОНБУД`=032016) — **20 записей**, «будильник
каналов». Формат (по заголовку таблицы в исходнике):

| Разряды | Поле |
|---|---|
| 33–38 | номер канала (сверяется с ТУСЗ) |
| 11–20 | ВРЕМЯ ОЖИДАНИЯ |
| 1–10 | **ЧИСЛО АКТИВНЫХ ЗАЯВОК НА КАНАЛЕ (ЧАКБВВ)** |

Каналы в таблице: `01 02 03 04 05 06 08 0A 0B 0C 0D 0F 1C 1D 20 25 24 22 21 23`
(шестнадцатерично). Канал МД **0x22** стоит по индексу 17 — и поиск в прогоне
завершается ровно за 18 итераций **[Н]**, что независимо подтверждает
`НУС = 0120`.

Вернувшись, `ВЫППВВ` делает:

```
И =В'1777'          ; ЧАКБВВ
ПО ОШД12            ; "НУС В ТУС НЕВЕРЕН" — если счётчик НУЛЕВОЙ
СЧ (Ц) ; ВЧ =В'1' ; ЗП (Ц)     ; ЧАКБВВ = ЧАКБВВ - 1
```

### 7.5. Как возобновляется ждущая задача **[Н][Л]**

Выдав обмен, задача паркуется в `ЖДИПР` (032332) — это **чистое ожидание
прерывания**, не семафор и не опрос состояния заявки:

```
ЖДИПР  РЕГ '140'   ГАШУ СКП
       VТМ 3                  ← гасит PSW_INTR_DISABLE: прерывания разрешены
       РЖА 7
       ПБ ЖДИПР               ← вечный цикл, выйти можно только по прерыванию
```

Возврат из прерывания (`ВЫХПР`, 032315) восстанавливает регистры и делает
`ВЫПР (3)` — то есть возвращается **в прерванную точку**, обратно в цикл
`ЖДИПР`. Пробуждение устроено иначе, через `АНАЛИЗ`:

```
ОБРПРЕ  32313  УИА АНАЛИЗ(13)        M13 := 032327 — точка возврата обработчика
ППВВ    32630  ПБ (13)               выход обработчика → АНАЛИЗ
АНАЛИЗ  32327  ПО ВЫХПР   БВВ НЕТ    ← СМ=0: заявки нет, обычный возврат
               ЗП СМ1  АДРЕС ПОЛУЧ ЗАЯВКИ
ВЫХПР   32321  СЧ СМ1                возобновляемый код получает адрес в СМ
        32322  ВЫПР (3)
```

То есть обработчик обязан выйти с **адресом завершённой заявки в сумматоре**;
тогда `АНАЛИЗ` кладёт его в `СМ1`, и задача просыпается, получив заявку.

**Путь `ППВВ`.** Проверка в 032601 — после цикла `ЦПБ` (032574-032600, «ПОИСК
СВС, ВЫДАВШ. БОЛЬШЕ ЗАЯВОК»), опирающегося на счётчики обменов `КОБМ`
(032035), — уводит на ветвь `НЕТБВВ` (032610). На этой ветви завершённая
заявка остаётся вне `ТВЗП[НСВС]`/`КОБМ`, СМ остаётся нулевым, и `АНАЛИЗ`
делает обычный возврат в `ЖДИПР` **[?]**. Заголовок `ППВВ` описывает другой
путь: «ИСКЛЮЧ ЗАЯВКИ ИЗ ДВР, ПОДКЛЮЧЕНИЕ ЕЕ В ТВЗП[НСВС]».

#### 7.5.1. Запрос ПВВ — уровень **[Н]**

Гасить `GRVP_INTR_IOM` обязан канал: АДАП его не гасит — во всём модуле
**одна** команда `РЕГ '47'`, и та относится к таймеру («ГАШУ ВРЕМ ПРЕР»);
ни `ППВВ`, ни `ГАСИПР` (он гасит *заявку*) к РВП не обращаются.

Разряд держится до конца обработки: `ОБРПРЕ` читает РВП (`РЕГ '247'`) уже
внутри обработчика, чтобы выбрать ветвь, и без разряда `ППВВ` не достигается.
Запрос — **уровень**: он стоит, пока голова очереди ответов (`iom->SQA`,
ДВРПВВ) непуста, и снимается, когда АДАП её обнулил. Это `iom_update_intr()`,
вызываемая перед проверкой `ГРВП & ГРМ`. На прогоне `ППВВ` = 2,
`ГАСИПР` = 2, `ВЫППВВ` = 2.

### 7.6. Пробуждение через межпроцессорное прерывание **[Н][Л]**

Разгадка §7.5: завершённую заявку задаче отдаёт **не** обработчик ПВВ, а
отдельное **межпроцессорное прерывание**, которое ПВВ-обработчик посылает
владельцу заявки — в однопроцессорной конфигурации самому себе.

```
ППВВ  32477  СЧСНХ ТВЗП(НСВС)          подцепил заявку в ТВЗП своего СВС
      32502  ДАЙ ЕСВС                  ЕСВС>>НСВС — разряд своего СВС
      32504  ИЛИ ПРЕР ; ЗП ПРЕР        "ЕМУ ПОШЛЮ ПРЕР"
      32610  СЧМ ПРЕР ; РЕГ '50'       "ВСЕХ ПРЕРВУ"
             ↓
ОБРПРЕ       НЕД(ГРВП&ГРМ) → ПБ ПРКЛПР-41(14)
ПРКЛПР 32306 УИА АНАЛИЗ-4(13) ; ПБ ПРСВС     ← ГРВП разр.8 = GRVP_REQUEST
ПРСВС  30020 … достаёт заявку, СМ := её адрес
АНАЛИЗ 32327 ЗП СМ1 ; ВЫХПР ; ВЫПР (3)  → задача просыпается в КНЦОБМ
```

Отображение разрядов ГРВП на входы `ПРКЛПР` (выведено из `НЕД`:
`n = svs_highest_bit`, переход `ПРКЛПР-41+n`, то есть вход = 41−n от разряда):

| n | разр. | ГРВП | вход |
|---|---|---|---|
| 41 | 8 | `GRVP_REQUEST` 0200 | **ПРСВС** |
| 42 | 7 | `GRVP_RESPONSE` 0100 | СТ102 «ОТВЕТ ОТ ПРОЦЕССОРОВ» |
| 43 | 6 | `GRVP_IOM_FAIL` 0040 | АВСВС «АВАРИЯ СВС» |
| 44 | 5 | `GRVP_RAM_FAIL` 0020 | СТ102 |
| 45 | 4 | `GRVP_TIMER` 0010 | ПРВРЕМ |
| 46 | 3 | `GRVP_INTR_IOM` 0004 | ПРПВВ |

Каждая метка совпадает по смыслу со своим разрядом — отображение подтверждено.

**Два требования к эмулятору.**

1. `РЕГ '50'` взводит **ПОП** по маске адресуемых процессоров (разр.39-42).
2. Взводить `GRVP_REQUEST` напрямую бесполезно: `cpu_one_instr` после **каждой**
   команды пересчитывает этот разряд как `(ПОП & РКП)`, так что прямая запись
   стирается на следующей же команде. Отсюда и требование: **разряд процессора
   в РКП обязан совпадать с `NSVS`** (СВС k — разряд 42−k). Для СВС 1 это
   `d RKP 1020000000000000`; для СВС 0 — `1040000000000000`.

## 7A. ГЕНС и барабаны (МБ) **[Л]**

Разбор `генс.bemsh` из `besm6.github.io/sources/dispak-svs`. ГЕНС = ГЕНерация
Системы; `ГЕНС СТАРТ '70000'` (ГЕНС1/ГЕНС2 — с '60000'), поэтому этап,
грузящийся в 070000, — это он. ВЫЗСВС читает его с МД зоны 0555 на страницу
034 (`КУСГЕН КОНД М17В'3'М12В'34'М24В'0555'`, 034₈×1024 = 070000) и уходит
`ПБ '70000'`.

### 7A.1 Роспись МБ — запись образца и контрольное чтение

`МБРОС` — поверхностный тест барабана: заполняет 1024 слова образцом
`КАННА5`/`К5АННА`, пишет зону (`ПВ ЗКМБ`), обнуляет буфер, взводит признак
чтения (`ИЛИ Е18`) и читает ту же зону обратно, после чего смотрит `ОШБ`.
Данные при этом **не сравниваются**: ГЕНС полагается на служебные слова и
тег-контроль. Отсюда наблюдаемая цепочка ЗП→ЧТ и сотни обменов.

После успешной записи `ПРБ6` подменяет страницу на 31/32, взводит `Е22Е18` и
уходит `ПБ ЗКМБ` — это и есть контрольное чтение.

### 7A.2 КУС барабана

`Еn` — константа с единицей в разряде n; ГЕНС раскладывает их по ячейкам
0103…0162 (`ИИ ЗП '103'+47(М16)`, где '103' восьмеричное, а 47 десятичное →
база 0162), так что **Еn лежит по адресу 0163−n**: Е1@0162, Е3@0160, Е4@0157,
Е6@0155, Е8@0153.

| Разряды | Смысл |
|---|---|
| 1–2 | номер абзаца (сектора), `Е2Е1 КОНД В'3'` |
| 3–7 | номер тракта (5 разр.) |
| 8–10 | номер МБ (3 разр.) |
| 13–17 | номер страницы ОП, `КСТР КОНД М12В'37'` |
| **18** | **чтение** (0 = запись), `И Е18 / ПО МБ5 ЗП НА МБ` |
| **19** | обмен страницей (иначе один абзац) |
| 24 | контрольное чтение — **гасится в `МБ7А` перед выдачей**, канал его не видит |
| 40–42 | номер направления |

### 7A.3 Служебные слова зоны МБ — 4 пары по секторам

Зона = 8 СС + 1024 слова = **4 сектора (абзаца) по 256 слов**. `ЗКМБ` при
записи (`МБ5`/`МБ6`) заполняет СС попарно:

* **чётное СС** — физический адрес сектора, собранный `СБР БТС` из КУС, где
  `БТС КОНД М39В'7'М2В'377'`: разр.3–10 — зона, разр.40–42 — барабан; сверх
  того `ПРБ3` подмешивает номер сектора (`СЧИ М2 / СДА 64-34`) в разр.36–37;
* **нечётное СС** — 12-разрядная контрольная сумма сектора.

Сумма (`КСМБ`): циклическая сумма (`СЛЦ`, с круговым переносом) 256 слов
абзаца, свёртка 48 разрядов в 12, затем четыре такие суммы пакуются по 12
разрядов в одно слово. **Нулевой абзац даёт нулевую сумму.**

При чтении (`МБ4`) ГЕНС, наоборот, **обнуляет** все 8 ячеек СС — данные СС
обязан принести барабан. Сверка на завершении чтения (`ПРБ3`/`ПРБ4`) идёт и по
адресу, и по сумме; `СДА 64-3` перед `ПЕ ПРБ7` исключает старшие 3 разряда
адреса из сравнения (АДАП подмешивает туда признак узла в `УПМБ`).

**Вывод для эмулятора:** от барабана требуется только **буквальный round-trip
всех 1032 слов вместе с тегами**.

Синтезировать «правильные» СС в непрописанной зоне **нельзя**: роспись сначала
пишет, а там, где ГЕНС читает чистый барабан (`РБ`: `СЧ КЛЮМК / НТЖ NМЛ+2 /
ПО РБА КЛЮЧ ВЕРЕН` → `РОСМК`), он ХОЧЕТ несовпадения ключа — именно оно
включает роспись. Пустая зона отдаётся нулями с тегами `TAG_INSN48`.

### 7A.4 Физический адрес зоны в СПУ: зона×32 + сектор×8 **[Л]**

АДАП кладёт в РМР слова СПУ не номер зоны, а физический адрес. Ветка МБ
(`адап.bemsh`):

```
МБ:    СЧМР / СДА 64-2        остаток ДАЙНБ (зона) * 4
       СЧМ СМ                 ... в стек
ОБСЕК: И =В'3' / СЛЦ -2(S)    + номер абзаца (0-3)
       СДА 64-3               всё * 8  =>  зона*32 + сектор*8
НПР:   СДА 64+16 В МР         младшие 16 разр. -> РМР
```

Деления пополам (как у МД по типу ёмкости) здесь нет — ветка `ПИО ДИСК(ТИП)`
на барабан не заходит. Делить на 32 обязательно: зоны 022300/026400/026440 из
трассы — это **294/360/361**, идущие подряд, и без деления файл барабана
растёт разреженным до 229 МБ при нужных 7 МБ.

Логический номер МБ и номер зоны АДАП получает в `ДАЙНБ`, деля плоский индекс
`(направление‖МБ‖тракт)` на **0707₈ = 455** зон на барабан.

### 7A.5 Прерывания и `СТОП '00301'`

Векторы ГЕНС: ячейка **'500'** ← `ЯЧ500`/`НОВ500` (внутреннее прерывание, КЧ →
`ПРКЧ`), ячейка **'501'** ← `ЯЧ501` → `ВНЕШПР` (внешнее). Ожидание завершения —
`ЖДИПР`/`ЖДЕМ` (71147/71154), сплошной спин.

`ВНЕШПР` упрятывает регистры и лишь потом читает ГРВП:

```
РЕГ '247' / МОДА МРВП / И / ЗП РВП
И Е4 / ПЕ ПРВРЕМ     (010 таймер)
И Е8 / ПЕ ПРЕСВС     (0200 СВС)
И Е3 / ПЕ ПРЕПВВ     (004 ПВВ)  → УИА ВОЗПРЕ(М15) / ПБ ПРПВВ, делегирует АДАП-у
И Е6 / ПЕ ПРЕРВС     (040)
ПБ СТ301             НЕОБРАБ.ВНЕШНИЕ ПРЕРЫВАНИЯ
```

То есть **`СТОП '00301'` — не таймаут**, а внешнее прерывание, прошедшее маску
и не совпавшее ни с одним из четырёх разрядов. ГЕНС ждёт именно **Е3 = 0004 =
`GRVP_INTR_IOM`**; 040 (`GRVP_IOM_FAIL`) уводит в `АВСВС` — аварию, а не
завершение.

Маска: в трассе видно **ГРМ = 0277**, что совпадает с `МГРП КОНД В'277'`
(`адап.bemsh:633`) — АДАП её и записывает. (`МРВП` ГЕНС импортирует —
`ПВВ ВНЕШ (МРВП,МГРП)`; единственное определение в дереве, `дисп80.bemsh:848
МРВП КОНД В'677'`, из другого модуля, так что 0277 против 0677 по исходникам
не разрешается — но регистр наблюдаемо равен 0277.)

Прочие останова: `СТ300` внутреннее прерывание, `СТ302` неверный ключ в СС
зоны МД (ключ 070707 в разр.39–25, `КССС`), `СТ303` неверная контрольная сумма
СС зоны МД; безномерной `СТОП 0` — несовпадение контрольной суммы при
контрольном чтении МБ (повтор записи по ПУСКУ). У ВЫЗСВС свой набор
00200–00210, в том числе `СТ201` — тот же «необрабатываемое внешнее».

### 7A.6 Состояние

При делении зоны на 32, возврате пустой зоны нулями и ограничителе обхода
ТОЧ `СТОП '00301'` не возникает: ГЕНС выполняет ~3,45 млн команд, проходит роспись
всех зон подряд (0…345₈, 481 чтение / 467 записей парами ЗП→ЧТ) и переходит к
`ЧТГП` — чтению зон ОС 565…570 с МД на страницы 11-30. Дальше канал получает
`Сброс ПВВ` и начинает читать как команды БАК посторонние слова
(`КОП=027 слово=0xd1782100f073`) — это следующий рубеж.

## 7Б. Сверка с заводской документацией (№10.170.002 ТОП) **[Д]**

`IOM_instruction_set.md` — OCR раздела 4 заводского описания ПВВ. Это первичный
источник, старше всех наших эмпирических выводов; пометка **[Д]** ниже означает
«из документа». Проверено: форматы документа разбирают РЕАЛЬНЫЕ слова из нашей
трассы без единого исключения.

### 7Б.1 КОП — четыре разряда (36-39)

Документ перечисляет коды двоичными тетрадами: ПОБ 0001, ЗК/ЗРК 0010,
ОК/ОРК 0011, **ИБАК 0100, ИТУС 0101, ИТОЧ 0110, ИДВР 0111**, ГРС 1000,
ГПС 1001, ПОБР 1010, ЦРВ 1100, АРВ 1101, МОП/МКФ 1110. Поля слова БАК:
**КОП разр.36-39, СБ (семафорный бит) разр.32, адрес разр.0-19.**

Разбор наблюдённых слов по этой раскладке:

| слово из трассы | КОП₄ | команда | СБ | адрес |
|---|---|---|---|---|
| `0x50000080f0` | 5 | ИТУС | 0 | 0100360 ✓ ТУС |
| `0x6000008160` | 6 | ИТОЧ | 0 | 0100540 ✓ ТОЧ |
| `0x70000082e8` | 7 | ИДВР | 0 | 0101350 ✓ ДВРПВВ |
| `0xd000000000` | 015 | **АРВ** | 0 | 0 |
| `0x1100000000` | 1 | **ПОБ** | **1** | 0 |
| `0xe90000000f` | 016 | **МОП/МКФ** | **1** | маска 017 |

Каждая строка сходится с АДАП-ом: `МБРСА` заканчивается
`СЧ =М20В'15' РЕЖИМ АРВ В ПВВ` (015 = 1101 = АРВ ✓) и
`СЧ КМКФК ... ПОДКЛ.ВСЕХ КАНАЛОВ` (016 = 1110 = МКФ ✓), а СБ взведён ровно у
тех двух команд, которые кладёт процессор.

В эмуляторе: `BAK_KOP(v) = (v >> 36) & 017` — четыре разряда, рядом
`BAK_SEM` (разр.32) и `BAK_NUS` (разр.54-63), адрес — 20 разрядов
(`& 03777777`). В трассе команды печатаются с именем
(`КОП=05 ИТУС СБ=0 НУС=0 адрес=100360`).

*Свойство, о котором стоит знать:* при четырёхразрядном КОП почти любое слово
складывается в ПРАВДОПОДОБНУЮ команду. Слово, попавшее в БАКПВВ после того как
образ ОС лёг поверх АДАП-а (§7Б.2 ниже и §8), читается как
`ИДВР адрес=170163`, и канал переставляет базу таблицы ответов. Поэтому на
смену уже установленной базы выдаётся предупреждение «ВНИМАНИЕ: ИДВР
переставляет базу X -> Y» (после сброса база нулевая, так что штатная
регистрация молчит).

### 7Б.2 ПОБ несёт НУС — канал обязан обслужить ОДНО устройство

> «Номер запускаемого устройства помещается в поле НУС слова команды ПОБ…
> Практически достаточно один раз выдать эту команду, чтобы ПВВ произвёл
> обслуживание всех заявок из очереди **к данному устройству**.»

НУС — разр.54-63 слова ПОБ. Далее (4.4): «Считывается слово ТУС по адресу
БАТУС + НУС, слово ТОЧ по адресу **БАТОЧ + 2НУС**».

**ПРОВЕРЕНО — АДАП этой формой НЕ пользуется.** Измерено по журналу заявок:
во всех **953** командах ПОБ нашего прогона **НУС=0**, само слово —
`0x1100000000`, то есть КОП|СБ и больше ничего. А работа всё это время лежит
ровно в двух очередях:

| ТОЧ | заявок | что это |
|---|---|---|
| **69** | 946 | барабан: класс 4 (база 0100) + устр.5 |
| **81** | 7 | диск: класс 5 (база 0120) + устр.1 |

Нулевой номер по 4.1.2 — не устройство, а служебный блок У ПВВ, так что ПОБ с
НУС=0 означает «просто поищи работу»: в автоматическом режиме АРВ канал
разбирает очереди сам, без участия ЦП (4.1). Реализовано так: **НУС≠0 —
обслуживаем ровно одну очередь, как написано в документе; НУС=0 — обход всей
таблицы.**

Следствие: **ограничитель длины цепочки и пропуск слотов с нулевым ДАЙМА
обязательны.** При НУС=0 канал заглядывает во все 112 слотов, включая
мусорные.

### 7Б.3 ДВР: разряд П — точная модель прерывания ПРПВВ

Формат ДВР: **МЦП** (маска ЦП), **П**, ИВС, СБ, **НАДР** (начало очереди
выполненных работ), **КАДР** (конец).

> «П — требование прерывания ЦП при включении очередной завершённой работы.
> **После прерывания ПВВ гасит этот разряд.**»

Это заметно точнее нашей уровневой модели («разряд держится, пока
`memory[SQA] != 0`»): по документу канал прерывает, только если ОС попросила
разрядом П, и сам же П гасит. Стоит примерить к `iom_update_intr`, когда
дойдут руки до §7.5.

### 7Б.4 Что документ ПОДТВЕРЖДАЕТ

* **БВ — семь слов в порядке СВ, ЛР, ДО, СО, СПУ, ДР, ДРУ.** Совпадает со
  смещениями эмулятора слово в слово и **опознаёт сл.1 как ЛР** (слово левой
  работы), которое мы просто не трогаем. Сл.7 (АКТЗ) — надстройка АДАП-а.
* **Нулевые ТУС и ТОЧ — не устройство, а обработка сбоев** («нулевой номер
  устройства присвоен блоку У ПВВ»). Это оправдывает отказ `iom_tus_class`
  работать с классом 0.
* **ТОЧ — пары слов НОЧ/КОЧ по индексу 2·НУС**, связь заявок через сл. СВ,
  адресное поле последнего звена нулевое.
* **СБ в БАК** взводит ЦП при записи команды, гасит ПВВ после расшифровки.
  Эмулятор обнуляет оба слова БАКПВВ целиком; по документу гасится только СБ.
* **Адрес в командах — 20 разр. (0-19).** Столько же берётся и под НАМ слова
  ДО (`memory[z+2] & 0xFFFFF`, §5.4), так что лист ≥ 0200000 адресуется.

### 7Б.5 Чего в эмуляторе нет вовсе

* **ЛР, «левая работа»** (4.1.5, 4.4): признак — разр.57 слова СО; заявка к
  устройству j вклинивается в обмен с устройством i. Слово ЛР несёт НУС, МПВВ
  и ЛАБВ.
* **КО, «круговой обход»** (4.4): обход устройств на обменнике по полям
  ПОУ/СОУ слова ТУС с разрядом БР.
* **ЦРВ/АРВ**: ПОБ работает только в АРВ, ПОБР — только в ЦРВ. АДАП
  устанавливает АРВ последней командой после сброса.
* **ПОБР (1010)**, ГРС/ГПС (оптимизаторы и ПД), ЗК/ЗРК, ОК/ОРК.

### 7Б.7 Адрес массива обмена — ФИЗИЧЕСКИЙ, приписка к нему не применяется

Адрес массива из ДО — физический: `mmu_iom_data_pa()` тождественна.

**Документ.** «НАМ — начальный адрес массива **в оперативной памяти**»; канал
«производит передачу информации между оперативной памятью (через коммутатор
связи) и внешним устройством **без участия секции управления**» (4.4).
Трансляция — отдельный необязательный режим **ДОП** («режим обработки таблицы
страниц сегментов», разр.50 слова СО) и только для быстрых каналов.

**АДАП.** Это видно прямо в исходнике: адреса СВОИХ структур он
пропускает через `ДФАПВВ` (= `СЛЦ АДРЕС`, «с точки зрения ПВВ»), а в ветке
формирования ДО никакого `ДФАПВВ` нет — там `СЧИ 8 НОМЕР ЛИСТА / СДА 64-10
АДРЕС`, то есть **лист × 1024**, где лист = страница из КУС плюс `БАЗАОС`
(база ОС). Это номер листа памяти.

**Почему это существенно.** АДАП перенесён на физические листы 32+, а образ
ОС читается на физические листы 11-30 — области не пересекаются. Приписка же
отправила бы виртуальные 030xxx в физические 0100xxx, то есть ровно на АДАП,
и зоны ОС легли бы поверх БАКПВВ/ТУС/ТОЧ/ДВРПВВ (§8).

**Измерено по журналу заявок** (`set cpu0 debug=dev`, без покомандной трассы):

| | |
|---|---|
| обменов | 1056 |
| затирание структур АДАП-а | 0 |
| «Сброс ПВВ» | 1, начальный |
| мусорных команд БАК | 0 |
| зоны ОС с МД | 565…633 подряд, затем 556, 100 |

Первые три обмена — 511/754/555, затем роспись барабана. Загрузка уходит в
низкую память, останов — `контроль команды` на 01450 (PC 01414).

### 7Б.8 РАЗМ из ДО: переносится только запрошенное

**РАЗМ** — размер массива в словах, разр.22-41 слова ДО (4.1.5). Он протянут
через `svs_disk_io()`/`svs_drum_io()` и дальше в `svs_*_read/write()`:
переносится ровно столько слов, сколько запрошено. Распределение РАЗМ по
журналу заявок:

| РАЗМ | заявок | что это |
|---|---|---|
| 1024 | 1011 | барабан, полная зона данных |
| 784 | 43 | диск, упакованная зона (0o1420, ср. `ДОМЛМД` = `М22В'1420'`) |
| **8** | **2** | **только служебные слова зоны** |

Заявка на 8 слов читает одни служебные слова зоны 0100 в 030..037 — проба
метки тома.

Два типа устройств считают РАЗМ ПО-РАЗНОМУ, и это видно из самих чисел:

* **МД:** РАЗМ=784 покрывает всю раскладку от НАМ — 8 служ. слов (смещения
  0-7), 8 неиспользуемых, 768 слов данных (с 16, `DISK_DATA_OFFSET`). Значит
  ограничение накладывается на смещение от НАМ целиком.
* **МБ:** РАЗМ=1024 — это ровно страница данных, без служебных слов: АДАП
  гоняет служебные слова барабана отдельной областью **СС1Н**
  (`КНАПР КОНД А(СС1Н)` в `ЗКМБ`), вне массива ДО. Поэтому у барабана РАЗМ
  ограничивает только данные, а служебные слова переносятся всегда.

**Частичная запись — чтение-модификация-запись.** Зона на носителе пишется
целиком, поэтому при неполном РАЗМ она сначала подтягивается с носителя, а
потом перекрывается только запрошенное (нет зоны — начинаем с нулей).

### 7Б.9 Номер зоны в служебном слове МД

Служебные слова зоны несут её номер, и ДИСКИ сверяет его со своим КУС2.

**Запись** (`диски.bemsh`, ОБ4А):

```
 СЧ КУС2-1(М16) / И Е36П25 / СДА 64-12 / ИЛИ (М10) / ЗП (М10) / ЗП 4(М10)
```

— поле зоны из КУС2 встаёт в разр.48-37, и одна и та же величина идёт в СС[0]
и в СС[4].

**Проверка** — `ПРЗОНЫ`, физ.073503 (в листинге `diski.txt` 73477: сборка
сдвинута на 4 слова, совпадение проверено по командам 73274-73277):

```
73503  сч РЯД / и Е31                ; затвор — разр.31 слова СС[1]>>12
73504  по НЕТЗОН / сч ФКУСД          ; ФКУСД = СС[0] прочитанной зоны
73505  сда 64-36 / зп РЯД2
73506  сч ФКУСД / сда 64+12          ; поворот вправо на 12
73507  или РЯД2 / нтж КУС2-1(М16)    ; поле зоны в разр.25-38, XOR с КУС2
73510  и 72504 / уиа ОШЗОНЫ(М10)     ; маска 0007777700000000
73511  пе ПЛОХО                      ; ОШЗОНЫ, «N ЗОНЫ НЕ СОВПАЛ»
```

Таблица масок в этой сборке: 72501 = 01777, 72502 = 07777, 72503 = 037777,
72504 = 077777; `Е34П25+2` попадает в последнюю, так что сверяется всё поле
зоны. Отсюда требование к образу: СС[0] и СС[4] несут тот же номер зоны,
который ОС кладёт в КУС2. `tools/makeSVS2053.py` ставит в разр.48-37 индекс
зоны в образе, не трогая прочие разряды и КС зоны `СС[3]`.

**Контрольная сумма зоны.** При взведённом разр.41 в `СС[1]` ГЕНС идёт по
ветви `НОВС` (генс.bemsh:519):

```
НОВС УИА -1023(М6)          1024 слова
     СЧ 0
КСН  СЛЦ 2047(М6)           циклическая сумма 02000..03777
     ЦИКЛ КСН(М6)
     ЗП РЯ1
     УИА 3(М10) / ПВ ЧТСЛ   читаем СС[3]
КСП  НТЖ РЯ1 / ПЕ СТ303     сравнение ПОЛНЫМИ 48 разрядами, без маски
```

Считается она по РАСПАКОВАННОЙ странице и на `svs2053.bin` сходится с `СС[3]`
побитно у зон 0511, 0555, 0460, 0462, 0463 — это независимая проверка свёртки
4:3 в `svs_disk.c`.

**Удвоение номера зоны в АДАП-е.** [Д] СПУ строится из КУС в ветке `ДИСК`
(вирт.034655-034676), и решает одно поле — **ТИП МД, разр.29-28 слова
`ТУСЗ[НУС]`**:

```
034655  мода 200(М7)      М20 := ТУСЗ = 030200
        счп 0(М3)         М3 = НУС (для системного МД 0121 = ТУСМД+1)
034656  сда 64+27 / и =В'3'
034657  уи 5              ПРЗЧ (М5) := ТИП МД
        сч 1540           СМ = КУС
034660  сда 64+24         зона из КУС (разр.38-25) в младшие разряды
        мода 1755(М7)     КВЗОН
034661  и 0(М5)           маска по типу: 01777 / 07777 / 037777 / 077777
        зп 0(М15)
034662  счи 5 / нтж =В'1'
034663  по 4676(М7)       ТИП = 1 (29 МГБ) → МД297
        сч 0(М15)
034664  сда 64-1          удвоение
        зп 0(М15)
034665  пио 34676(М5)     ТИП = 0 (7,25 МГБ) → МД297
        ...               ТИП = 2 (100 МГБ) → правка СПУ
034676  МД297: сч 0(М15) / и =В'177777'  → 16 разр. в РМР слова СПУ
```

ТИП = 1 (29 МГБ) оставляет номер как есть; 0 (7,25 МГБ), 2 (100 МГБ) и 3 его
удваивают. В `adap.b6` вместо исходных `СЧИ ПРЗЧ / НТЖ =В'2' / ПЕ МД297` стоит
`ПИО МД297(5)` (отмечено в `adapcmp.b6`), поэтому в ветку «100 МГБ» уходит и
ТИП = 3. МБ сюда не попадает: вход — `ПИО ДИСК(ТИП)`, а `МБТИП ЭКВ 1`.

**ТУСЗ в прогоне.** На каждом обмене с МД `М5 = 2`, `М3 = 0121`, то есть диски
объявлены 100 МГБ:

```
физ. 0100320:  0506 1021 0051 7705   МД 0      (разр.29-28 = 2)
физ. 0100321:  0512 1021 0051 7705   МД 1      системный диск
физ. 0100322:  0516 1021 0051 7705   МД 2
```

Значение приходит из самого АДАП-а: шаблон `ТУСМД КОНД (16)М32Х'22'М27В'2'…`
(`М27В'2'` = ТИП 2), статическая копия лежит по 030500 и читается как
`0002102100517700`. В рабочей ТУСЗ от шаблона отличаются старшие разряды
(номер устройства) и «смесь» = 5.

*При отладке:* живая ТУСЗ лежит по физ.0100320. `РПС3 = 0017 0042 0041 0040`
отображает вирт. страницы 12-14 (адреса 030000-035777) на физ.040-042, а
`cpu_examine` ходит в физическую память мимо приписки.

На `svs2053-fixed.bin` дисковый этап проходит целиком: 75 обменов с МД, опрос
барабанов 0-4, роспись барабана 5 зонами 0440-0537 (64 зоны).

### 7Б.10 Барабан: сектор и раскладка массива обмена

[Д] За зоной 0462 следует чтение **барабана 5, зона 0512, сектор 3**. Два
требования к модели МБ, оба видны по заявке:

```
ЗП  зона=512 сектор=0  ДО=…(НАМ 0046000 РАЗМ 1024) СПУ=…(РМР 024500)
ЧТ  зона=512 сектор=3  ДО=…(НАМ 0012000 РАЗМ  256) СПУ=…(РМР 024530)
```

РМР = зона*32 + сектор*8: 024500 = 0512*32, 024530 = то же + 3*8.

1. **Сектор доходит до устройства.** Зона МБ делится на ЧЕТЫРЕ сектора по
   256 слов (`ZONE_SECTORS`/`SECTOR_WORDS`), сектор 3 — последняя четверть;
   РАЗМ=256 у секторной заявки это подтверждает. `svs_iom.c` передаёт номер
   сектора в `svs_drum_io()`, а тот сдвигает на него индекс в образе, оставляя
   адрес в памяти прежним: на этом расхождении двух индексов и держится
   разница между полной и секторной заявкой.

2. **Массив обмена МБ — это ТОЛЬКО данные, с самого НАМ.** Служебные слова
   зоны АДАП возит отдельной заявкой («чтение СС», разр.21 КУС, своя длина
   ДЛССД) в область СС1Н (`КНАПР КОНД А(СС1Н)` в ЗКМБ), в массив ДО они не
   входят, и класть их по НАМ нельзя: данные сдвинулись бы на 8 слов.
   У МД раскладка обратная: РАЗМ=784 покрывает и служебные слова
   (`DISK_DATA_OFFSET`).

Заявки идут по всем четырём секторам (0, 1, 2, 3).

Рубеж — ОС уходит в цикл «ЧТ/ЗП барабан 5, зона 0444, буфер 0110000» и за
200 млн команд не печатает больше ничего.

На конфигурации `dispak.ini` с исходным `svs2053.bin` останов — ОШЗОНЫ на
зоне 0462.

### 7Б.6 Несходится и требует разбирательства

ТУС по документу несёт **тип устройства отдельными разрядами** (МЛ — лента,
СД — сменный диск, МБО — барабан под оптимизатором) плюс НЕК (номер базового
канала), ПОУ/СОУ, БР, БЗ, НС, ИР, НИК, СВ. **Поля «номер класса» в документе
нет**, а `iom_tus_class` читает младшие 12 разр. записи как номер класса
(4 — МБ, 5 — МД) и это эмпирически работает (§5.3). Два прочтения не сходятся;
до разбора код не трогать.

## 8. Текущее состояние

**РАСПАК достигнут.** Полная цепочка проходит без единой ошибки:

```
ФОРБВВ → ЛНУТУС/ЛОКОБ (ЛУ 031 → НУС 0121) → ВКЛТОЧ → НУСЕС → ДИСПАК → ТЕСОБМ
  → ЧАКБВВ+1 → РЕГ '50' → канал: обмен → ДВРПВВ + ГРВП разр.3
  → ППВВ → ГАСИПР → АКТИВ → ВЫППВВ → ИНДБУД → ТВЗП[НСВС] + ПРЕР
  → РЕГ '50' → ПРСВС → АНАЛИЗ → ВЫПР(3) → КНЦОБМ → ВОСМД → РАСПАК
```

| Точка | Срабатываний |
|---|---|
| `ТЕСОБМ` 034311 / `ЧАКБВВ+1` 034316 | 2 / 2 |
| `ППВВ` 032334 / `ГАСИПР` 032400 / `АКТИВ` 032410 | 2 / 2 / 2 |
| `ВЫППВВ` 032514 / `ИНДБУД` 035427 | 2 / 4 |
| `РЕГ '50'` 032610 / `ПРСВС` 030020 / `АНАЛИЗ` 032327 | 2 / 4 / 4 |
| **`КНЦОБМ` 032232** | **2** |
| `ВОСМД` 034735 / **`РАСПАК` 034700** | 2 / **2** |
| `ОШДВР2` / `ОШД12` / `ОШДВР` / `СТ115` / `СТ100` | 0 / 0 / 0 / 0 / 0 |

Обмен выполняется по правильным параметрам:

```
iom0 --- обмен: устр=1 заявка@31100 ЧТ зона=511 буфер=42016
```

**РАСПАК отрабатывает и распаковывает страницу ВЕРНО** (§5.4.1: свёртка S/D и
порядок групп; первые слова совпадают с образом диска). Зона читается по
правильному адресу (`обмен: устр=1 заявка@31100 ЧТ зона=511 буфер=2360`),
контроль числа и `СТ101` не срабатывают (`КЧ`=0, `СТ101`=0), цикл распаковки
`ЦИКР` проходит все 768 упакованных слов.

**Где стоит сейчас** (`./boot.sh`, `svs.ini` на `svs2053-fixed.bin`): загрузка
проходит дисковый этап и роспись барабана 5, дальше ОС крутит
«ЧТ/ЗП барабан 5, зона 0444, буфер 0110000».

Распакованная «вызывалка» ложится по физ. 03402000 (трасса записи:
`Memory Write [02000 3402000]`; вирт. стр. 1 → физ. 0o1601 по RPS0), а переход
на 02000 в режиме супервизора выбирает команду **без приписки** и попадает в
пустую физ. 02000. Содержимое страницы при этом уже правильное — упирается
только модель приписки.

**Это упирается в модель приписки, а она в эмуляторе упрощена.** В СВС приписка
включена ВСЕГДА — и для команд, и для данных; `VТМ` переключает не вкл/выкл, а
ЧЬЯ приписка применяется к ДАННЫМ (ядра или пользователя), тогда как выборка
команд в режиме ядра всегда идёт по приписке ядра. Правильный вариант написан и
закомментирован в `va_to_pa()`/`mmu_fetch()` (`#if 0`). С ним АДАП доходит лишь
до 036134 (`РЕГ '60'+РПАД`, «НАСТР. 14,15,16,17 РАФОС») и падает по контролю
команды: неизвестно, какой должна быть **начальная** приписка ядра и
пользователя. `ПЕРЕП` (036034) при этой модели — не самокопирование, а
настоящий перенос: читает по приписке ядра (`VТМ 1027`), пишет по приписке
пользователя (`VТМ 1024`), «ПЕРЕПИСЬ АДАПТЕРА ВО 2-Ю П/СЕКЦИЮ» **[?]**.

## 9. Открытые вопросы и упрощения в эмуляторе

1. **ДРУ (слово 6)** — назначение разрядов не установлено; пишется 0 **[?]**.
2. **Тип ёмкости устройства** должен читаться из `ТУСЗ[НУС]` и задавать
   масштаб зоны (§5.4); сейчас делитель 2 зашит в `iom_xfer_zaiavka` **[?]**.
3. **ТВЗП (031270)** — адрес зашит константой `IOM_TVZP`; команды регистрации
   для неё не наблюдалось, в отличие от УТ/ТОЧ/ОТВ (§4.2).
4. **Контроль тега (КЧ)** отключён намертво в `svs_mmu.c`
   (`if (0 && tag_check && …)`), так как загрузчик метит все слова 035/036.
5. **Цепочка из нескольких одновременных завершений** через ТОЧ не реализована:
   канал связывает с ДВРПВВ ровно одну заявку.
6. **Многопроцессорность** (`RKP` на cpu1) не реализована в эмуляторе.
7. **Модель приписки.** Правильный вариант (приписка всегда включена, `VТМ`
   выбирает ядро/пользователя для данных, команды в режиме ядра — всегда по
   ядру) написан и закомментирован в `va_to_pa()`/`mmu_fetch()`. Не хватает
   начальной приписки ядра и пользователя — см. §8.

## 11. Тонкие места

### 11.1. `ПЕРЕП` затирает таблицы через неприписанную страницу **[Н]**

Цикл `ПЕРЕП` (036034, 3072 итерации) копирует АДАП **сам в себя**: читает с
включённой припиской (`VТМ 1024`), пишет с выключенной (`VТМ 1027`). Приписка
страниц 12–15 на себя обязательна, её задаёт строка
`d RPS3 0017001600150014` (страницы 14,15,16,17₈ = 12–15). Без неё чтение идёт
с физической страницы 0 (умолчание `va_to_pa`) и цикл забивает нулями
загруженные `ТУС`/`ТУСЗ`/`ТУСМД`.

### 11.2. Пустые головы таблиц **[Н]**

`ТУСЗ`(030200) и `ТУС`(030360) начинаются с блока класса 0, который в этой
конфигурации пуст; содержимое идёт со смещения 020. Смотреть надо **весь**
диапазон (`e 30200-30357`, `e 30360-30537`).

### 11.3. Незавершающийся `go` и гигабайтная трасса **[Н]**

`set cpu0 debug=insn` пишет ~3 МБ/с, а голый `go` с недостижимой точкой останова
не завершается никогда: за четверть часа трасса вырастает до десятков
гигабайт. Удаление файла не возвращает место, пока его держит открытым хоть
один читающий процесс (`grep` по трассе).

Меры:

- прогонять через `./runsim.sh [ini] [лимит-ГБ] [таймаут-с]` — сторож снимает
  симулятор при превышении лимита (по умолчанию 2 ГБ / 300 с);
- вместо голого `go` использовать ограниченный `step N` — он тоже
  останавливается на точке останова, но не может идти вечно;
- после разбора удалять `dispak.trace` (в начале `dispak.ini` есть
  `! rm -f dispak.trace`, но он срабатывает только на следующем прогоне).

### 11.4. Буферизация вывода симулятора

При перенаправлении в `head`/`tail` вывод буферизуется целиком и появляется
только в самом конце; перенаправлять надо в файл.

### 11.5. Псевдонимы регистров **[Л]**

Один регистр обычно имеет несколько имён:

| Рег. | Имена |
|---|---|
| 1 | НСВС |
| 2 | АЗАЯВ, R |
| 3 | НШГ, НР, **НУС** |
| 4 | ТИП |
| 5 | АДР |
| 6 | R1, СЛЕД |
| 7 | БАЗА |
| 14 | ВОЗВ, Ц, М16 |
| 15 | S, М17 — **он же указатель аппаратного стека** (017₈) |

Отдельного имени `М7` нет — используется `(БАЗА)`.
